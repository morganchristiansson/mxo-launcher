# VTable `0x004b8034` - `CLTTCPConnection`

## Why this file was updated

A previous correction pass fixed the stale `0x449ca0` / `0x449cd0` naming, but it also over-compressed the row listing.
This file now keeps the corrected meanings **and** restores the full visible vtable row inventory.

## Current high-confidence correction

Earlier notes treated:

- `0x449ca0` as `CBaseConnection::IsConnected`
- `0x449cd0` as `CLTTCPConnection::Close`
- `0x449d20` as `CLTTCPConnection::~CLTTCPConnection`

That mapping is not supported by the current direct assembly/decompilation pass.

Current best read is:

- `0x449ca0` = shared connection **Close** wrapper into engine slot `+0x1c`
- `0x449cd0` = connection **Connect** wrapper that updates endpoint `+0x24` then calls engine slot `+0x18`
- `0x449d20` = connection **SendBuffer** wrapper that forwards `(buffer, byteCount, this, completion)` into engine slot `+0x20`
- `0x449d40` = `CLTTCPConnection::OnReceive`
- `0x449fd0` = `CLTTCPConnection::OnClose`

## Key setup anchors

### `0x44a9f0 = CBaseConnection_ctor`

- temporarily installs `0x004b8018`
- stores engine pointer at connection `+0x10`
- zeroes endpoint copies at `+0x14` and `+0x24`
- writes state `+0x34 = 8`

### `0x44aad0 = CLTTCPConnection_ctor`

- overwrites the vtable with `0x004b8034`
- stores the framing-parser helper at connection `+0x6c`

### `0x44ac40 = CLTTCPConnection_dtor`

- destructor / deleting-dtor family member, not a constructor

## Recovered field map

High-confidence connection fields from the corrected pass:

- `+0x10` = owning engine pointer
- `+0x24` = copied endpoint key used by the connect wrapper
- `+0x34` = connection state
  - `8` is the closed/inactive state checked by `0x449ca0`
- `+0x6c` = framing parser pointer used by `0x449d40`
  - now narrowed further to a `CVariableLengthPrefixedTCPStreamParser` family object

## Corrected wrapper behavior

### `0x449ca0 = CLTTCPConnection_Close`

Assembly shape:

```asm
cmp [ecx+0x34], 8
jz  return_zero
mov eax, [ecx+0x10]
push param_1
push ecx
mov ecx, eax
call [edx+0x1c]
```

Current best interpretation:

- if state is already `8`, returns `0`
- otherwise forwards `this` plus the caller flag/arg into engine slot `+0x1c`
- this matches a close/abort wrapper, not a no-arg `IsConnected()` query

### `0x449cd0 = CLTTCPConnection_Connect`

Assembly/decompile shape:

- compares incoming endpoint against connection `+0x24`
- if changed:
  - calls the `0x449ca0` close wrapper with `0`
  - copies the new 16-byte endpoint into `+0x24`
- then calls engine slot `+0x18` with `this`

Current best interpretation:

- `CLTTCPConnection::Connect(const Endpoint& endpoint)`

### `0x449d20 = CLTTCPConnection_SendBuffer`

Assembly shape:

```asm
mov ecx, [this+0x10]
push completionContext
push this
push byteCount
push buffer
call [edx+0x20]
```

Current best interpretation:

- `CLTTCPConnection::SendBuffer(buffer, byteCount, completionContext)`

### `0x449d40 = CLTTCPConnection_OnReceive`

Important confirmed shape from the current pass:

- connection `+0x6c` is a `CVariableLengthPrefixedTCPStreamParser` family object
  - primary callee: `0x469bf0 = CVariableLengthPrefixedTCPStreamParser_Parse`
- the explicit second arg is now best read as a refcounted `CLTTCPReadOperation`-family
  **buffer fragment**, not a generic callback object and not a completed packet work item
  - evidence:
    - worker-thread receive path allocates `0x100c`, installs vtable `0x004b2300`, zeroes `+0x04`
      and `+0x08`, then immediately calls fragment `+0x04`
    - fragment methods at `0x42f850 / 0x42f860 / 0x42f880 / 0x42f890` operate on `+0x04` through
      `InterlockedIncrement` / `InterlockedDecrement` / `InterlockedExchange`
    - parser/work-item helpers treat it as `{vtable, refCount, byteCount, bytes...}`
    - `CMessageConnection::OnOperationCompleted` logs leftover fragment bytes as
      `Unused buffers were attached to CLTTCPReadOperation ...`
- the early `readOperationFragment->+0x04` is now narrowed from “maybe prep” to
  **AddRef / retain only**
  - exact stack shaping from the assembly:

```asm
lea eax, [ebp-0x8]     ; &completedPacketWorkItem
push eax
push ecx               ; temporary scratch, later overwritten
mov edi, ecx           ; save connection this
mov ebx, [edi+0x6c]    ; parser
mov eax, esp
mov [eax], esi         ; top stack dword becomes readOperationFragment
mov ecx, esi
call [edx+0x4]         ; readOperationFragment->AddRef()
mov eax, [ebx]
mov ecx, ebx
call [eax+0x4]         ; parser->Parse(readOperationFragment, &completedPacketWorkItem)
```

  - because the fragment `+0x04` call does **not** clean those prepared stack dwords, they remain
    in place for the immediately following parser call
- later drain calls are the cleaner explicit shape:
  - `parser->Parse(0, &completedPacketWorkItem)`
- repeated zero-result parses enqueue `(completedPacketWorkItem, this, 0)` through
  engine helper `0x436820`
- terminal positive / non-`0x7000000` parse results log and then call `this->+0x0c(0)`
- the final `readOperationFragment->+0x08` in `0x449d40` releases only the **outer**
  OnReceive-held fragment reference
  - `Parse` itself also takes and releases its own transient fragment reference
  - `CParsedPacketWorkItem_AppendFragment` retains fragments that become owned by the completed
    work item
- parser input fragment currently narrows to:
  - worker-thread receive vtable = `0x004b2300`
  - worker-thread receive allocation size = `0x100c`
  - `+0x04` = interlocked refcount
  - `+0x08` = byte count
  - `+0x0c` = first fragment byte
  - vtable `+0x00` = deleting-dtor-style entry
  - vtable `+0x04` = no-arg AddRef
  - vtable `+0x08` = no-arg Release
  - vtable `+0x10` = reset refcount to zero
  - vtable `+0x14` = set refcount from pointed-to value
- parser-emitted `workItem` currently narrows to:
  - the `0x2c` / vtable-`0x4b3e08` work-item family built by `0x435db0 -> 0x435090`

### `0x449fd0 = CLTTCPConnection_OnClose`

Current best confirmed behavior is still only the fragment release, but one concrete caller now
narrows the wider ABI shape:

- assembly of `0x449fd0` itself:
  - loads the **first stack arg** into `ecx`
  - if non-null, calls `fragment->+0x08()`
  - ignores incoming member `ecx`
  - returns with `ret 0xc`
- concrete worker-thread UDP receive caller at `0x0043034f..0x0043036e` prepares:
  - arg1 = `readOperationFragment`
  - arg2 = pointer to a copied 16-byte peer/source address blob
  - arg3 = immediate `0x004b2118`
  - then calls connection vtable `+0x18`
- `0x449fd0` ignores that wider call shape and only consumes/release-balances arg1
- source keeps a convenience wrapper around the only confirmed effect, but the original member ABI is
  now concretely known to be wider than a single-argument wrapper

## Source lockstep update

Current source files updated to follow this corrected mapping:

- `matrixstaging/runtime/src/liblttcp/lttcpconnection.h`

In particular:

- the engine pointer is now treated as base `CLTTCPConnection` state, matching `0x44a9f0`
- `CMessageConnection` no longer keeps a duplicate source-owned engine field
- `lttcpconnection.h` now carries an explicit `CLTTCPReadOperation`-family fragment scaffold plus
  the now-confirmed fragment vtable surface at `+0x00 / +0x04 / +0x08 / +0x0c / +0x10 / +0x14`
- that scaffold now names `+0x04` as the interlocked fragment refcount based on the concrete
  worker-thread producer and fragment-method bodies
- `CLTTCPConnection::OnReceive` now models the narrower AddRef / Parse / Release seam directly and
  no longer returns a source-only synthetic success value
- source `OnClose(...)` now records the wider original callback ABI with two opaque trailing stack
  args while still implementing only the confirmed fragment-release effect
- source comments now treat connection `+0x6c` as a parser-owned receive seam rather than a generic anonymous poll helper
- current source also now keeps an explicit queue-context bridge beside `CBaseConnection` because
  the starter C++ vtable layout is still not byte-faithful to the original queue consumer's
  `context->vtable[4]` (`+0x10`) dispatch expectation
  - this is a source-owned ABI bridge only
  - it exists so the now-live parsed-packet receive path can still reach
    `CMessageConnection::OnOperationCompleted` faithfully enough without pretending the current C++
    class vtable layout already matches original launcher layout
