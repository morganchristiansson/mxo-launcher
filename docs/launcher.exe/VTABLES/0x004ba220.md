# VTable `0x004ba220` - reset-time / base outer `CMessageConnectionMessage` table

This is the **base/reset-time outer table** used by the message-ref object family around:
- `0x455bd0 = CMessageConnectionMessage_ResetForPacketBuilder`
- `0x455c60 = CMessageConnectionMessage_Create`
- `0x455cd0 = CMessageConnectionMessage_CreateRef`

The live created object does **not** stay on this table.
`0x455c60` first runs `0x455bd0`, which installs `0x004ba220`, then immediately overwrites the
object vtable to:
- `0x004ba23c`

So `0x004ba220` is best read as the **base / transitional outer table**, with `0x004ba23c` as the
final live derived table.

## Object layout this table belongs to

Current best outer raw layout from `0x455bd0` / `0x455c60`:
- `+0x00` = vtable (`0x004ba220` during reset, later `0x004ba23c` live)
- `+0x04` = refcount dword
- `+0x08` = ctor/reset argument preserved by `0x455bd0`
- `+0x0c` = pointer to the inner payload-storage object (`0x004ba208` family)
- later live-only fields then begin at:
  - `+0x10` = headerless flag
  - `+0x14/+0x18/+0x1c/+0x20` = extra context / zeroed state

## Why this table is base/transitional rather than final live state

The strongest proof is slot `+0x0c`:
- `0x004ba22c -> 0x48bc34 -> purecall`

That means a refcount-to-zero `Release()` while still on `0x004ba220` would be invalid.
So this table is not meant to be the final public/live vtable used by the completed object.

That matches the create path exactly:
- `0x455bd0` installs `0x004ba220`
- allocates/resets the inner `0x004ba208` payload object
- stores it at outer `+0x0c`
- then `0x455c60` overwrites the outer vtable to `0x004ba23c`

## Destructor behavior

`0x4557f0`:
- first installs `0x004ba220`
- releases the inner payload object at outer `+0x0c`
- then installs base refcounted vtable `0x004b211c`
- then optionally frees the outer storage

So the current best inheritance-like chain is:
- `0x004b211c` = common refcounted base
- `0x004ba220` = outer message-ref base/reset-time table
- `0x004ba23c` = live derived outer message-ref table

## Role of slot `+0x18`

`+0x18 = 0x4557b0` is the key outer-object helper.
It does **not** grow an external vector; it updates the inner payload-storage length bytes via the
outer object's pointer at `+0x0c`.

Recovered behavior:
- load inner payload object from outer `+0x0c`
- read current length from inner `+0x0a/+0x0b`
- add requested byte count
- if result `< 0x1001`, write the new length back to inner `+0x0a/+0x0b`

Current source cleanup now follows that contract more directly too:
- outer grow paths update the inner raw `+0x0a/+0x0b` bytes first
- source no longer treats a vector mirror as the primary receive-side payload state there

That is the main reason the outer object and inner payload object must be documented together.
