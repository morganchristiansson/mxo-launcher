## Queue-thread main-body meaning

`0x436fc0` / `CLTThreadPerClientTCPEngine_QueueThread_Run` is a tiny wrapper:

```c
void __thiscall CLTThreadPerClientTCPEngine_QueueThread_Run(void *this)
{
    CLTBaseThreadPerClientTCPEngine_RunCompletedOperationQueue(*(void **)((int)this + 0x38), '\0');
}
```

So the queue-thread child is not a complex worker with its own large private body.
It is mainly a generic thread wrapper that:
- remembers its owning engine at `+0x38`
- then runs the owner's **blocking** completed-operation consumer loop
  - `0x436b10` / `CLTBaseThreadPerClientTCPEngine_RunCompletedOperationQueue(owner, 0)`

That directly explains why the client-side non-blocking poll path later looks structurally similar:
- queue-thread body uses the blocking `nonBlocking = 0` form
- `RunClientDLL` later reaches the analogous non-blocking consumer form with `nonBlocking = 1`

That makes the queue-thread object layout currently read as:

## Start / stop / wait / dtor semantics on this object

Because this vtable inherits almost all of the generic thread base unchanged, queue-thread lifecycle semantics are currently the shared `CLTThread_*` ones:

- **start**: `_beginthreadex(... CREATE_SUSPENDED ...)`, optional priority mapping, then `ResumeThread`
- **stop**: if called from the worker thread itself, immediately `ExitThread(0)`; otherwise may `TerminateThread(handle, 0)` and optionally wait
- **wait**: `WaitForSingleObject(handle, INFINITE)`
- **dtor**: shared `CLTThread_dtor` closes the thread handle, deletes the lock, and frees the stored name string

So the queue-thread-specific behavior is mainly in its thread main body, not in a special lifecycle implementation.
