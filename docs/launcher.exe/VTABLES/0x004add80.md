# 0x004add80 - LogRouter

## Overview

`0x004add80` is the vtable for the launcher's shared logging / trace router object.

Current evidence:

- `FUN_00403990` allocates `0x20c` bytes and constructs this object
- `LogRouter_Construct` (`0x414a70`) installs vtable `0x004add80`
- `LogRouter_FormatAndDispatchSinkMessageV` (`0x414be0`) is the main formatter / dispatcher that routes formatted TLS text into the sink methods and callbacks owned by this object

This is **shared infrastructure**, not a `loginmediator.cpp`-specific object.
It is still very useful for static RE because the surrounding helper family preserves original source-file / line metadata and lets us anchor many callsites back to translation units.

## Default constructor behavior

`LogRouter_Construct` currently proves:

- the whole route table at `+0x04` defaults to sink id `3`
- all sink-enabled bytes are zeroed first
- sink id `3` is then enabled at `+0x0fa`

So the default router behavior is:

- **all routeGroup/detailLevel pairs map to sink 3**
- **only sink 3 is enabled by default**
- sink 3 body is `LogRouter_OutputDebugStringTlsMessage`

That makes the default live behavior a shared `OutputDebugStringA` trace sink.

A now-better-understood alternative sink path is sink id `1`, which publishes log state into two global console variables:

- `gConsoleColorVar` at `0x004d3d70` (`CConsoleInt`, named `"ConsoleColor"`)
- `gConsoleTextVar` at `0x004d3db0` (`CConsoleString`, named `"ConsoleText"`)

Current safest interpretation:

- these are real global console-variable objects, not guessed labels
- sink id `1` writes message color/context into `gConsoleColorVar`
- sink id `1` writes the formatted TLS text into `gConsoleTextVar`
- the ultimate consumer of those console vars is still not fully recovered from direct xrefs here, so treat the broader UI/console-display role as likely but not yet fully closed

Those globals are initialized by:

- `0x004987d0` `InitializeConsoleColorVar`
- `0x00498800` `InitializeConsoleTextVar`

### Important boundary after the vtable

The vtable ends at slot 7.
Data immediately after it is **not** more virtual slots:

- `0x004add9c` -> `"%s: "`
- `0x004adda4` -> `"%s(%i) : "`

That matters because older rough dumps can accidentally over-read the vtable here.

## CWinApp_InitInstance interaction

`CWinApp_InitInstance` gives an especially useful concrete configuration example.
When the launcher is given a log-file path:

- it calls vtable slot 1 / `LogRouter_OpenFileSink(6, path, 0)`
- enables sink `6` with `LogRouter_SetSinkEnabledState`
- installs sink `6`'s prefix callback via `LogRouter_SetSinkPrefixCallback`
- remaps **all** detail levels to sink `6` via `LogRouter_MapDetailLevelToSink(9, 6)`

So the launcher can switch from the default OutputDebugString path to a file-backed trace path very early in startup.

## Static-RE value

This vtable matters beyond plain logging:

- the router family carries original `sourceFile` / `sourceLine` metadata
- many functions either pass `.cpp` paths directly or stage them in TLS before logging
- those staged values are strong translation-unit anchors for static RE

Canonical companion doc for that source-file anchoring use:

- `../logging/TRACE_ROUTER_AND_FILE_ANCHORS.md`

## Confidence

High for:

- `0x004add80` being the shared log router vtable
- object size `0x20c`
- route-table / sink-enable / file-sink / TLS-slot layout above
- default routing to sink `3` / `OutputDebugStringA`
- vtable ending at slot 7 with string data immediately after it

Medium for:

- naming `DAT_004d3d70` as a primary-sink format/state object
- naming `DAT_004d3db0` as a primary-sink consumer object

Those two globals are definitely part of the primary sink path, but their deeper concrete types remain to be recovered more explicitly.
