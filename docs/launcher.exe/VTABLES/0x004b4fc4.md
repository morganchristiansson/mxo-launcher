# 0x004b4fc4 - CLTLoginState_State1

## Overview
Best current concrete candidate for the missing **state `1`** login-state object.
This is an 8-byte object in the helper dispatch table (`vptr` + cached upstream pointer at `this+4`)
and sits directly on the early auth-connect path.

Provisional better-name suggestion:
- `CLTLoginState_AuthConnectPending`

## Why this is now a state-1 match
- slot 3 is `0x00439090 = CLTLoginMediator_Helper1_StartAuthConnection`
- that body caches the upstream object at `this+4` and calls `CLTLoginMediator_BeginAuthConnection`
- slot 7 is `0x0044e360`, which is the tiny `mov eax,1 ; ret` stub
- slot 10 is `0x00439060`, which installs vtable `0x004b4fc4`

## Key specialized methods
- `0x00439090` is the strongest identity anchor: it is the helper-1 auth-connect start body.
- `0x004390b0` is now tighter than a generic “state-specific gate” label:
  - type-`2` work only; everything else falls back to shared slot-1 gate `0x00438d80`
  - payload copy: `owner +0x80 = workItem +0x08`
  - zero payload side:
    - read cached upstream helper state id through `[this+4]->vtable+0x18`
    - `0x41b450(stateId)`
    - new helper slot 3 receives old-state `this`
    - `0x41cfb0(0)`
  - non-zero payload side:
    - `owner +0x2c = 1`
    - retry gate uses owner `+0x28` against the dword-count of the owner auth-address span
      `(+0x50 - +0x4c) >> 2`
    - retry branch calls this object's slot 3 with cached upstream `this+4`
    - exhausted branch zeroes owner `+0x28`, `0x41b450(0)`, then `0x41d090(0)`
- `0x0044e360` closes the loop by proving that slot 7 returns state id `1`.
