# 0x004b4fc4 - CLTLoginState_State1

## Overview
Best current concrete candidate for the missing **state `1`** login-state object.
This is an 8-byte object in the helper dispatch table (`vptr` + cached upstream pointer at `this+4`)
and sits directly on the early auth-connect path.

Provisional better-name suggestion:
- `CLTLoginState_AuthConnectPending`

## Why this is now a state-1 match
- slot 3 is `0x00439090 = CLTLoginMediator_Helper1_StartAuthConnection`
- that body caches the upstream object at `this+4` and calls `CLTLoginMediator_BeginAuthConnection`
- slot 7 is `0x0044e360`, which is the tiny `mov eax,1 ; ret` stub
- slot 10 is `0x00439060`, which installs vtable `0x004b4fc4`

## Composition notes
- This fills the previously missing concrete **state `1`** position between `CLTLoginState_State0` and `CLTLoginState_AuthenticatePending`.
- Structurally it fits the same Family B auth/bootstrap branch as the other early auth-side helpers.
- Current source ownership tightening:
  - `loginstate_state1.cpp` now owns the slot-3 auth-connect start scaffold directly
  - `CLTLoginMediator::BeginAuthConnectionViaState1Scaffold()` now owns the narrow state-1 entry
    ceremony for the live diagnostics auto-begin path:
    - capture current helper as the upstream/cached state1 input
    - install the registered state1 scaffold as current helper
    - call `CLTLoginState_State1::Slot3_BeginOrContinue`
  - diagnostics no longer manually sets current state to state1 before invoking slot 3
  - mediator auth connect-status handling is now narrowed to: record payload first, then route to
    state1 slot 1 on the active state1 path; this preserves the cached-status contract that slot 1
    consumes through `LastAuthConnectStatus()`
  - the later connect-status continuation is still only partially faithful because the original
    `0x4390b0` retry/error path around owner `+0x28/+0x4c/+0x50` is not source-owned yet
