## Key specialized methods
- `0x004401a0` is one of the best anchored methods in the create-character branch.
  Current strongest static read:
  - slot 3 sibling `0x43bf90` first sends raw margin opcode `0x0a = MS_ClaimCharacterNameRequest`
  - slot 6 therefore consumes the matching raw margin opcode `0x0b = MS_ClaimCharacterNameReply`
  - non-`0x0b` packets are rejected in-place with owner `+0x80 = 0x12000005`
  - error replies do **not** continue into helper11/state11
    - instead they switch helper state to `3` and post error `0x0b`
  - successful replies:
    - allocate a new slot record into owner `+0x688[currentCount]`
    - copy the selected world-descriptor inline name into owner `+0x818[currentCount]`
    - write owner `+0xcc8 = currentCount`, then increment owner `+0x684`
    - copy current `CharacterName` (`+0x108`) plus parsed reply ids into that slot record
    - set slot-record world id from owner `+0xd84[owner+0x12c]`
    - switch helper state to `0x0b`
    - post event `0x14`
  - immediate continuation after that success is now tighter too:
    `0x43c020 -> 0x440320 -> 0x439780 -> 0x41de40`
- `0x0043bf90` is now re-read as a gated small packet-builder/send body:
  - first gate: `0x41b4b0`
    - owner `+0x1c` must be non-null
    - connection state field `+0x34` must equal `2`
    - otherwise original switches helper state to `4`
  - second gate:
    - owner byte `+0xf14` must be non-zero
    - otherwise original switches helper state to `6`
  - packet-builder family:
    - `0x43a1f0` initializes a tiny raw-`0x0a` packet object
    - `0x43aa80` copies owner `+0x108` into the packet's `CharacterName` field
  - then it sends through `0x41af70` and posts event `0x13`
- source ownership consequence:
  - the active scaffold now keeps that slot-3 body in
    `matrixstaging/game/src/libltclientlogin/loginstate_state10.cpp`
    as `CLTLoginState_State10::Slot3_BeginOrContinue`
  - slot 6 ownership is now kept there too:
    - `CLTLoginState_State10::Slot6_HandleSecondaryMessage`
      is the current source-owned entry that consumes staged margin
      `MS_ClaimCharacterNameReply` bytes, rejects non-`0x0b`, mirrors the error-vs-success branch,
      and advances into helper11 only on success
    - the create-branch raw-`0x0b` append helper now lives in
      `CLTLoginState_State10::HandleStagedClaimCharacterNameReplyScaffold`
      and mirrors the bounded original owner writes to `+0x688/+0x818/+0xcc8/+0x80`
    - separate broader auth-reply adoption still lives in
      `CLTLoginState_State10::HandleStagedAuthReplyScaffold` /
      `CLTLoginState_State10::AdoptAuthReplyIntoRecoveredMediatorStateScaffold`, but that broader
      table rebuild should no longer be confused with the narrower original `0x4401a0` body
  - the local packet-builder family is source-owned there too as:
    - `0x43a1f0 = CLTLoginMediatorPacket0x0a_ResetAndInitialize`
    - `0x43aa80 = CLTLoginMediatorPacket0x0a_SetCharacterName`
  - mediator only keeps the narrow shared gates/transport/staging helpers:
    - `0x41b4b0` connection-state check
    - `0x41af70` current-connection send helper
    - staged incoming margin-packet bytes for the later slot-6 path
- Slot 7 (`0x00438ca0`) returns `10`, which matches the idea that this is the helper immediately before the create-character helper11/state11 stage.
