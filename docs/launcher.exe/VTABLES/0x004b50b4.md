## Key specialized methods
- `0x0043ba20` is the outbound half and is much smaller than the neighboring helpers.
  Newer decompile/disassembly tightening now makes the exact gates and payload much clearer:
  - first gate: owner `+0x1c` ready-state through `0x41b4b0`; on failure it switches helper state to `4`
  - second gate: owner byte `+0xf14`; on zero it switches helper state to `6`
  - then it initializes local raw margin packet `0x43a9a0`
    - opcode `0x0d`
    - fixed dwords at payload `+0x03/+0x07`
  - it copies current character/source name through the same `0x43aa80` string writer family
  - it copies the current slot-record id pair from owner vtable `+0x44`
  - then sends through `0x41af70` and posts event `7`
- `0x0043bae0` is the matching inbound half.
  Newer tightening now closes event `8` more concretely:
  - it accepts only opcode `0x0e`
  - it stores parsed result dword `+0x09` into owner `+0x80`
  - then always switches helper state back to `3`
  - if result `< 1`, it posts event `8`
  - otherwise it posts error `9`
- practical consequence for the launcher-side upstream bridge:
  - the concrete `0x40ec70 -> +0xf0 -> state7 -> event 8` corridor is now best read as a
    delete-character / removal path
  - negative result: this event-`8` corridor is therefore **not** the hidden success-side producer
    for owner `+0xec = 0x41c1f0`
- Slot 7 (`0x00438c80`) returns `7`.
