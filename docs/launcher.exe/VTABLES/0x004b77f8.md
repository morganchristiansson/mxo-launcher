# 0x004b77f8 = Crypto++ FileSink-family object

Status: high confidence for Crypto++ family, medium confidence for exact concrete class name.

## Why this is Crypto++

Constructor `0x447b50` builds the object with named parameters that match Crypto++ exactly:

- `"OutputFileName"`
- `"OutputBinaryMode"`

Those strings are defined in `third_party/cryptopp890/argnames.h` as:

- `CryptoPP::Name::OutputFileName()`
- `CryptoPP::Name::OutputBinaryMode()`

And Crypto++ `FileSink` in `third_party/cryptopp890/files.h` initializes with the same pair:

```cpp
FileSink(const char *filename, bool binary=true)
    {IsolatedInitialize(MakeParameters(Name::OutputFileName(), filename)
        (Name::OutputBinaryMode(), binary));}
```

So `0x447b50` is not a launcher-local file helper. It is a Crypto++ file-output sink construction path.

## Current best mapping

| Address | Best mapping |

| `0x004b77f8` | Crypto++ `FileSink` family / configured file-output sink object |
| `0x447b50` | ctor/config-init path for Crypto++ `FileSink`-style object |
| `0x447dd0` | caller that constructs this sink for `pubkey.dat` output |

## Observed launcher usage

`0x447dd0` constructs this object with:

- output file name = `pubkey.dat`
- binary mode = `true`

Then it serializes, in order:

1. reply public-key id via `0x437ef0`
2. modulus integer object via virtual sink write path
3. public exponent integer object via the same path
4. a trailing NUL byte via `0x444640`
5. a fixed `0x100`-byte blob from the signature pointer via sink virtual `+0x14`

So the object at `0x004b77f8` belongs in the Crypto++ file sink / buffered transformation family, while
`0x447dd0` remains a launcher auth helper that uses that Crypto++ sink.

## Caution

Do not overclaim the exact leaf type yet.

This is very likely either:

- `CryptoPP::FileSink`, or
- a thin derived / wrapped old-Crypto++ file sink type produced by the launcher's older Crypto++ build.

The family identification is strong; the exact leaf name is still slightly open.
