# VTable `0x004b2300` - `CLTTCPReadOperation`

## High-confidence identity

This vtable belongs to the read-buffer fragment object family passed into the connection front-end
receive seam.

Current best concrete class name:
- **`CLTTCPReadOperation`**

Evidence:
- `CLTThreadPerClientTCPEngine_WorkerThread_Run` allocates `0x100c` bytes for this object on both
  TCP and UDP receive paths
- `CMessageConnection::OnOperationCompleted` logs leftover fragment bytes as:
  - `Unused buffers were attached to CLTTCPReadOperation from %d.%d.%d.%d:%d.`
- `CLTTCPConnection::OnReceive` (`0x449d40`) and
  `CVariableLengthPrefixedTCPStreamParser::Parse` (`0x469bf0`) use this object's virtual `+0x04`
  / `+0x08` as AddRef / Release hooks

## Recovered field layout

High-confidence layout from the worker-thread producer plus the vtable methods:

- `+0x00` = vtable
- `+0x04` = interlocked refcount
- `+0x08` = byte count
- `+0x0c` = first payload byte
- allocation size on the active worker-thread receive path = `0x100c`
  - i.e. inline storage for up to `0x1000` bytes beginning at `+0x0c`

Ghidra/source lockstep note:

- the current Ghidra prefix struct now names this 12-byte front matter as:
  - `vftptr_0x0`
  - `referenceCount04`
  - `byteCount08`
- parser helpers and `CLTTCPConnection::OnReceive` now also decompile against that tighter prefix
  more cleanly

## Method behavior

### `0x0042fd50 = CLTTCPReadOperation_dtor`

Assembly/decompile shape:
- overwrites the vtable with base `0x004b211c`
- if `(deleteFlag & 1) != 0`, frees the object through `0x452520`

Current best interpretation:
- deleting-dtor-style entry at vtable `+0x00`

### `0x0042f850 = CLTTCPReadOperation_AddRef`

```asm
add ecx, 4
push ecx
call InterlockedIncrement
```

Current best interpretation:
- interlocked increment of object `+0x04`

### `0x0042f860 = CLTTCPReadOperation_Release`

```asm
lea eax, [ecx+4]
push eax
call InterlockedDecrement
test eax, eax
jnz  return
mov edx, [ecx]
jmp [edx+0xc]
```

Current best interpretation:
- interlocked decrement of object `+0x04`
- when the count reaches zero, dispatches vtable `+0x0c`
  - on this vtable that is `Pointer_DeleteIfNonNull`
  - which in turn calls vtable `+0x00(1)`

So the zero-count release path is:
- `Release()`
- `-> Pointer_DeleteIfNonNull(this)`
- `-> deleting dtor(this, 1)`

### `0x0042f880 = CLTTCPReadOperation_ResetRefCount`

Current best interpretation:
- `InterlockedExchange(&this->refCount, 0)`

### `0x0042f890 = CLTTCPReadOperation_SetRefCountFromPtr`

Current best interpretation:
- `InterlockedExchange(&this->refCount, *valuePtr)`

### `0x00452350 = CLTTCPReadOperation_SetByteCount`

Current best interpretation:
- clamps incoming count to `0x1000`
- writes the result to object `+0x08`

## Concrete producer shape

`CLTThreadPerClientTCPEngine_WorkerThread_Run` now gives a direct static construction/use pattern.

### TCP receive path

The worker thread:
- allocates `0x100c`
- writes:
  - `vtable = 0x004b2300`
  - `refCount = 0`
  - `byteCount = 0`
- calls `CLTTCPReadOperation_AddRef()`
- receives into `object+0x0c`
- calls `CLTTCPReadOperation_SetByteCount(recvLen)`
- calls connection vtable `+0x14`
  - current best read: `CLTTCPConnection::OnReceive(readOperationFragment)`
- then drops its outer reference with `readOperationFragment->Release()`

### UDP receive path

The worker thread builds the same object family, then prepares a wider call to connection vtable
`+0x18`:
- arg1 = `readOperationFragment`
- arg2 = pointer to a copied 16-byte peer/source-address blob
- arg3 = immediate `0x004b2118`

The current inherited `CLTTCPConnection::OnClose` implementation ignores args 2/3 and only releases
arg1, but this caller proves the original callback ABI is wider than a single-stack-arg wrapper.

## Relationship to the parser seam

This object is the concrete front-end input consumed by:
- `0x449d40 = CLTTCPConnection::OnReceive`
- `0x469bf0 = CVariableLengthPrefixedTCPStreamParser::Parse`

Current best ownership model:
- worker thread takes **two** refs on the TCP receive path:
  - one outer worker-owned ref immediately after allocation/setup
  - one delivery-temp ref immediately before the connection callback
- `OnReceive` takes another temporary reference before its first parser handoff
- `Parse` takes/releases its own transient reference while appending retained fragments into the
  completed packet work item
- `0x435e60 = CParsedPacketWorkItem_AppendFragment` itself also ends with a trailing
  `Release(param_1)`
  - so that helper consumes one caller-held temp ref during the parser/work-item handoff
- the post-callback worker-thread release drops only the delivery-temp ref, leaving the earlier
  worker-owned ref in the chain
- that extra worker-owned ref is what makes the faithful `0x435e60` trailing-release behavior and
  later work-item teardown line up on the live path again

  `matrixstaging/runtime/src/liblttcp/lttcpconnection.h/.cpp`
  - the source no longer uses a hand-built fragment vtable struct for this family
  - payload `+0x0c` is now represented as the variable-length tail that begins immediately after
    the 12-byte class prefix (`sizeof(CLTTCPReadOperation) == 0x0c`)
  - the derived deleting dtor still explicitly collapses the native source object back to the
    shared base contract before final free so the recovered lifetime shape stays visible in code
- `CLTTCPConnection::PollReceiveAndDeliverReadOperationFragmentsScaffold()` now mirrors the active
  TCP receive delivery shape from `0x42fe50` more tightly:
  - allocate a source-owned `CLTTCPReadOperation`-family fragment with `0x1000` payload capacity
  - construct the real `CLTTCPReadOperation` class prefix instead of manually stuffing a fake
    vtable record
  - take one worker-owned outer ref immediately after allocation/setup
  - call `recv(..., fragment+0x0c, 0x1000, 0)` directly into the fragment payload
  - on terminal EOF/error, source now routes the transport shutdown through the same lower close

  - parser / consumer code now computes payload begin/end directly from the recovered `+0x0c`

  - take one more delivery-temp ref just before `OnReceive(readOperationFragment)`
  - call `OnReceive(readOperationFragment)`
  - drop only that delivery-temp ref after the callback returns
  - current bounded source gap there is now narrower than before:
