# 0x004abfe0 - CLauncher

## Overview

`0x004abfe0` is the vtable installed by the constructor at `0x4097f0` for the launcher's global main object at `0x4d3368`.

Current best canonical identity:

- **`CLauncher` vtable**

This is the main launcher application object that derives from MFC `CWinApp` and owns the startup path rooted at `0x40b430`.

## Evidence

### Constructor installs this vtable

Ctor `0x4097f0` does:

```asm
mov ecx, <this>
call 0x48ba5a          ; CWinApp::CWinApp thunk
mov dword ptr [esi],0x4abfe0
mov dword ptr [esi+0xa8],0xffffffff
mov byte ptr  [esi+0xb0],0x0
mov dword ptr [esi+0xa4],0x0
```

So `0x004abfe0` is the concrete vtable for the launcher-owned subclass, not plain base `CWinApp`.

### The owning object is the launcher global at `0x4d3368`

Static initializer `0x494bd0` constructs the global object at `0x4d3368` with `0x4097f0`.

Startup driver `0x40b430` then uses that object as `this` for launcher-specific methods including:

- `0x40a380`
- `0x40a780`
- `0x40a420`
- `0x40a4d0`
- `0x40b360`

That ties this vtable directly to the main launcher application object.

### `InitInstance` override is on this vtable

Slot `+0x58` points to `0x40b430`, which is the main startup driver currently named `CWinApp_InitInstance` in Ghidra.

Newer entry-flow tightening from the PE entrypoint `0x48be94`:
- CRT startup eventually calls `AfxWinMain(GetModuleHandleA(NULL), NULL, commandLineTail, showWindow)`
- so `0x40b430` is reached through normal MFC GUI application startup
- practical consequence: the missing launcher-owned login/selection gate should now be sought either
  inside `0x40b430` itself or in the MFC/launcher environment it pumps before the `0x40b7af..0x40b7c7`
  client-load corridor, not by inventing a separate top-level post-`InitInstance` caller for
  `0x40a4d0`

That body clearly performs launcher-specific work:

- early environment / prerequisite checks
- log-router configuration
- `ParseCommandLine`
- `CConsoleVar_ParseCommandLineAndConfig`
- `AfxInitRichEdit`
- launcher network/environment bringup
- `cres.dll` / `client.dll` loading
- `InitClientDLL` / `RunClientDLL` / `TermClientDLL` lifecycle through helper `0x40a4d0`

So this slot is the concrete launcher override:

- **`CLauncher::InitInstance` = `0x40b430`**

## What this vtable currently looks like structurally

The table is mostly inherited `CWinApp` / MFC virtual surface with only a small number of launcher-owned concrete overrides currently identified.

A practical current reading is:

- many entries in the `0x48b7xx .. 0x48baxx` range are imported MFC thunks
- some mid-table entries are shared no-op placeholders
- the important launcher-owned slots currently recovered are:
  - deleting destructor at `+0x04`
  - `InitInstance` override at `+0x58`

Do **not** overclaim the unresolved slots yet.
