# VTable `0x004b2134` - shared 12-byte work-item root

## Current best identity

This looks like the small common root/prefix family used by several queued TCP engine work-item
objects.

Current best concrete layout:

| Offset | Meaning | Confidence |
|---|---|---|
| `+0x00` | vtable | proven |
| `+0x04` | work-item type/code | strong |
| `+0x08` | status/payload dword | strong |

## Visible vtable rows

| Address | Target | Current best read |
|---|---:|---|
| `0x004b2134` | `0x42f940` | base dtor |
| `0x004b2138` | `0x4199b0` | `Pointer_DeleteIfNonNull` |

## Evidence

### Destructor shape

`0x42f940` is a tiny destructor that:

- restores vtable `0x004b2134`
- optionally frees `this`

That matches a generic root/base work-item class rather than a large concrete leaf.

### Shared prefix helper evidence

Two helper-style reads match this exact prefix shape:

- `0x4816f0 = CLTThreadPerClientTCPEngine_WorkItemHeader_GetWorkType`
  - returns `this->+0x04`
- `0x434d00 = CLTThreadPerClientTCPEngine_WorkItemHeader_GetStatusOrPayloadDword`
  - returns `this->+0x08`

So the current best generic ABI view is:

```c
struct CLTThreadPerClientTCPEngine_WorkItemHeader {
    void** vtable;              // +0x00
    uint32_t workType;          // +0x04
    uint32_t statusOrPayload;   // +0x08
};
```

## Relationship to `CParsedPacketWorkItem`

Current best static read is that `CParsedPacketWorkItem` (`vtable 0x004b3e08`) is a concrete leaf
on top of this root.

Evidence:

- `0x435090 = CParsedPacketWorkItem_ctor`
  - writes `+0x04 = 3`
  - writes `+0x08 = 0`
  - then installs vtable `0x004b3e08`
- `0x435f30 = CParsedPacketWorkItem_dtor`
  - after parsed-packet-specific fragment cleanup, retables the object back to `0x004b2134`

So the current best split is:

- `0x004b2134` = common root/prefix family
- `0x004b3e08` = parsed-packet derived family

## Scope caution

Do **not** over-collapse every work-item-like family into this exact concrete vtable.

This doc describes the best current **shared root / prefix** visible from:

- helper reads of `+0x04/+0x08`
- generic destructor shape
- derived parsed-packet teardown

Some larger work-item-adjacent families (for example the unresolved `0x004ba948` wrapper family)
may still expose or resemble parts of this prefix without themselves being this exact concrete root
object.
