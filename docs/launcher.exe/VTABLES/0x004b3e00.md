# VTable `0x004b3e00` - type-1 close work item

## Current best identity

This is the small queued `0x0c` work-item family used for close / peer-closed completion
submission.

High-confidence evidence:

- current Ghidra names:
  - `0x435070 = CLTThreadPerClientTCPEngine_CloseWorkItem_ctor`
  - `0x435840 = CLTThreadPerClientTCPEngine_CloseWorkItemPool_AllocateStorage`
  - `0x435240 = CLTThreadPerClientTCPEngine_CloseWorkItemPool_Clear`
  - `0x435c80 = CLTThreadPerClientTCPEngine_CloseWorkItem_dtor`
  - `0x435da0 = CLTThreadPerClientTCPEngine_CloseWorkItem_Allocate`
- ctor `0x435070`
  - writes `+0x00 = 0x004b3e00`

- producer families in the engine worker/close path use `0x435da0 -> 0x435840 -> 0x435070`
- `0x435840` is a dedicated small fixed allocator method over the global pool object at `0x004cb42c`
  - current Ghidra global names on that allocator state are now:

- deleting dtor `0x435c80` returns the object to that same pool free list
- queue consumer `0x436b10` treats work type `1` specially by running arg5 slot `12`

## Layout

| Offset | Meaning |
|---|---|

| `+0x08` | zeroed status/payload dword |

## Runtime role

Current best read on the launcher auth/margin path:

- worker detects peer-close / terminal close condition
- allocates `0x0c` via `0x435da0`
- constructs via `0x435070()`
- enqueues `(workItem, context=connection, queueSelect=0)`
- queue consumer first reaches `CleanupConnection(context)`
- then the same direct connection object continues through the normal auth/margin completion
  fallback path
