# 0x004b0e48 - LaunchPadClient

## Overview
LaunchPad-owned status-handler vtable for the pre-auth account / subscription / play-request layer.
This is **not** the `CLTLoginState_*` family. Its concrete success handlers now matter because they
perform the currently strongest recovered writes into the mediator owner's shared launch/session
state before the later state8/state11 margin senders consume that state.

Important negative result from the latest vtable/xref pass:
- `launcher.exe:0x4207c0` / the body that logs `LaunchPad login successful.` is **not** part of
  vtable `0x004b0e48`
- that function belongs to `CLTLoginState_State16` vtable `0x004b0bb0` slot 8 instead
- so the launchpad family hands off into the later auth-connect chain indirectly through the
  login-state family, not through an extra `LaunchPadClient_OnConnectionStatusCheck` vtable entry
- separate boundary note: the global `g_LaunchPadGateState16State18` is also read by
  `0x41ecd0`, `0x420360`, and earlier startup `0x406470`, but those reads belong to the
  mediator/login-state/startup side logic rather than this `LaunchPadClient` status-handler vtable

## Key specialized methods

### `0x00421220 = LaunchPadClient_OnLoginRequestStatus`
Strongest currently recovered **login-request success** writeback into the mediator owner.

Success branch (`resultCode == 0`) does all of the following before later subscription gating:
- calls mediator vtable `+0x144` first
- pushes stack arg `[ebp+0x14]` into owner vtable `+0x14c`
  - `0x41f330 = CLTLoginMediator_SetSharedMarginPacketField660`
  - writes owner `+0x660`
- pushes stack arg `[ebp+0x10]` into owner vtable `+0x150`
  - `0x41f270 = CLTLoginMediator_SetLaunchPadSourceBlock94FirstString`
  - writes the first inline string of owner `+0x94`
- logs `Session %s` from stack arg `[ebp+0x20]`
  - important negative result: this success path does **not** directly write owner `+0x664`

That makes this handler the best current concrete writer for the paired `+0x660` half of the
shared launch/session family consumed later by the post-auth margin builders.

Source ownership now lives in:
- `matrixstaging/game/src/libltclientlogin/launchpad.cpp`
- `matrixstaging/game/src/libltclientlogin/loginmediator.h`
- `matrixstaging/game/src/libltclientlogin/loginmediator.cpp`

### `0x00420ef0 = LaunchPadClient_OnPlayRequestStatus`
Strongest currently recovered **play-request success** writer for `GameSessionID`.

Success branch (`resultCode == 0`) does all of the following:
- copies callback string arg `[ebp+0x10]` into mediator owner `+0x664`
- then dispatches connection status / clears launchpad-local string state / advances launcher flow

The concrete string copy is:
- destination: owner `+0x664`
- later getter: `0x41f320 = CLTLoginMediator_GetGameSessionId664`
- later consumers:
  - `0x43bd20 = CLTLoginState_State8` slot 3 sender
  - `0x43c020 = CLTLoginState_State11` slot 3 sender

So the current strongest source-level conclusion is:
- `GameSessionID` is launchpad/play-request owned
- it is **shared** between state8 and state11 senders
- it is **not** the same thing as the branch-specific helper11-only writers for
  `+0x178/+0x198/+0x1b8`

Source ownership now lives in:
- `matrixstaging/game/src/libltclientlogin/launchpad.cpp`
- `matrixstaging/game/src/libltclientlogin/loginmediator.h`
- `matrixstaging/game/src/libltclientlogin/loginmediator.cpp`

## Current source-level consequence
The reimplementation now keeps these launchpad-owned writes out of `loginmediator.*` commentary and
mirrors them from `launchpad.cpp` into source-owned mediator state through the concrete recovered
setter surfaces:
- `0x41f330 = CLTLoginMediator_SetSharedMarginPacketField660`
- `0x41f270 = CLTLoginMediator_SetLaunchPadSourceBlock94FirstString`
- `SetGameSessionId664(...)` as the source-owned owner `+0x664` mirror

That keeps later state8/state11 send scaffolds reading the same shared mediator-side
`GameSessionID` path while preserving launchpad ownership of the writer side.
