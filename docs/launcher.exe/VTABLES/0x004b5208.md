# 0x004b5208 - CLTLoginState_State3

## Overview
Another concrete final-leaf variant built on the `0x004b51b8` shape. Also allocated directly as an 8-byte object with byte `+4 = 0`.

Provisional better-name suggestion:
- `CLTLoginState_SelectionContextPending`
- rationale: live original runs now show state `3` as the current helper immediately before the
  owner-side selection-context writers `0x41c390/0x41c1f0` advance into states `7/8`

## Key specialized methods
- The main differentiator here is slot 7: `0x00438cf0` is the tiny undefined-in-Ghidra getter that returns `3`.
- Like `0x004b51e0`, it reuses the same slot-6 handler (`0x004397e0`), the same zero-return slot 9 stub, and the same shared constructor target.
- That combination makes this a concrete **state-code specialization**, not a wholly separate behavioral class.

## Composition notes
- This is another live leaf under the `0x004b51b8` abstract-style node.
- newer runtime+owner evidence now makes its practical role less generic than the old `State3` name:
  - live original launches reach this as the current helper immediately before
    `0x41c390 = CLTLoginMediator_SetSelectionIndexAndSwitchToState7`
    and `0x41c1f0 = CLTLoginMediator_PersistSelectionContextAndSwitchToState8`
  - corrected happy-path WineDbg now tightens the lead-in too:
    - after the early auth chain `state0 -> state2 -> state1 -> state2`, the next proven switch is
      `state2 -> state3`
    - `0x41c1f0` is then reached while owner `+0x10` still points at vtable `0x004b5208`
    - a second fresh rerun with the correct password again reached `0x41c1f0` directly from that
      state-`3` wait period, with no additional early helper-switch hits in the narrow breakpoint set
  - that is why `CLTLoginState_SelectionContextPending` is now a reasonable provisional alias
- Its only meaningful concrete override relative to the sibling leaves is the slot-7 state-id getter.
