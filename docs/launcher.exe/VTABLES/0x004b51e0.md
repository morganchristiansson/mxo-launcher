## Key specialized methods
- Its specialized behavior is almost entirely encoded by the **combination** of slot 6 (`0x004397e0`), slot 7 (`0x00437b50` returns `0`), and the dispatch-table initialization byte `this+4 = 0`.
- Because slot 10 still uses `0x00439d80` (which installs `0x004b51b8`), this variant seems to be selected by direct vtable installation in the dispatch table rather than by a unique constructor.
- This makes it look much more like a concrete **state specialization** than a traditional standalone class.
- Newer init-path tightening now shows it is also the **initial current helper**:
  - `0x41b160 = CLTLoginMediator_Initialize`
  - after `0x43b300 = CLTLoginMediator_InitializeHelperDispatchTable`
  - the launcher writes `owner + 0x10 = DAT_004f7868`
  - and `DAT_004f7868` is the `0x004b51e0` object

## Composition notes
- This is one of the live leaves hanging off the abstract-style `0x004b51b8` node.
- The common family theme here is still “tiny `CLTLoginState` state object”, not `LaunchPadClient` in the broad sense.
- Current best practical flow read is now:
  - state `0` is the startup / pre-submit current helper installed at mediator init
  - it does **not** currently look like a state with its own concrete slot-3 transition body, because slot 3 is still the shared tiny stub `0x00441790`
  - the active password-submit path instead leaves state `0` through mediator owner code `0x41ecd0 = ProcessLoginRequest`, which switches to helper/state `2`
  - helper/state `2` (`0x004b5014`) then either:
    - re-enters state `1` to begin the auth transport connection when auth is not ready yet, or
    - continues directly into the auth-bootstrap dispatcher when the auth transport is already ready
- So the current evidence favors **initial idle/start state** over “state0 directly transitions to state1 by its own state-local body”.
