# 0x004af2b8 ILTLoginMediator abstract base candidate

Best current read: `0x004af2b8` is the **abstract base/interface vtable** immediately above
`0x004b01c8 = CLTLoginMediator`.

## Why this now fits `ILTLoginMediator`

Static evidence tightened by the current destructor pass:

- `0x41f810 = CLTLoginMediator_DeletingDestructor`
  - calls `0x41f6a0 = CLTLoginMediator_Destructor`
  - then optionally frees `this`
- `0x41f6a0 = CLTLoginMediator_Destructor`
  - first retables `this` to concrete owner vtable `0x004b01c8`
  - performs full owner cleanup/reset/vector/tree/string destruction
  - then retables `this` back to `0x004af2b8` before returning
- `0x41b0f0 = ILTLoginMediator_DeletingDestructor`
  - only retables `this` to `0x004af2b8`
  - optionally frees `this`
  - does **not** perform concrete owner-field cleanup
- raw PE dump of `launcher.exe` shows the exposed `0x004af2b8` virtual surface is almost entirely
  `0x48bc34 = ImportThunk_48bc34 -> purecall`
- that is the classic shape of a pure abstract interface/base, not a concrete owner object
- its exposed span stops at `+0x18c`, while concrete `0x004b01c8` continues one slot further with
  owner-only `+0x190 = 0x41f840 = CLTLoginMediator_AppendLateEntryStringTriple1470`

Taken together, this is a strong static fit for the source-side abstraction already modeled as
`ILTLoginMediator`.
