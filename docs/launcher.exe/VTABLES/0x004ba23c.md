# VTable `0x004ba23c` - live outer `CMessageConnectionMessage` receive/message-ref table

This is the **final live outer message-ref table** produced by:
- `0x455c60 = CMessageConnectionMessage_Create`
- `0x455cd0 = CMessageConnectionMessage_CreateRef`

It is the table that matters on the later receive/message-ref path used by:
- `0x4490c0`
- `0x41bc20`
- `0x41bbb0`
- later owner/callback consumers such as callback84-side client paths

## Construction path

`0x455c60 = CMessageConnectionMessage_Create` does:
1. allocate `0x24` bytes for the outer object
2. call `0x455bd0 = CMessageConnectionMessage_ResetForPacketBuilder`
   - installs base/reset-time vtable `0x004ba220`
   - allocates/resets inner payload-storage object `0x004ba208`
   - stores that inner object at outer `+0x0c`
3. overwrite outer vtable with `0x004ba23c`
4. zero/init the live tail fields:
   - `+0x10 = 0`
   - `+0x14 = 0`
   - `+0x18 = 0`
   - `+0x1c = 0`
   - `+0x20 = 0`

`0x455cd0 = CMessageConnectionMessage_CreateRef` then:
- calls `0x455c60`
- writes caller arg2 to outer `+0x14`
- returns the new outer object through the caller-provided output slot
- immediately AddRefs the created object through outer vtable `+0x04`

## Inheritance-like relationship

Current best family chain:
- `0x004b211c` = common refcounted base contract
- `0x004ba220` = base/reset-time outer message-ref table
- `0x004ba23c` = live derived outer message-ref table

What `0x004ba23c` specifically overrides relative to `0x004ba220`:
- `+0x00`
  - base/reset-time dtor `0x4557f0`
  - live derived dtor `0x455b40`
- `+0x0c`
  - base/reset-time purecall slot
  - live final-release helper `0x455b80`

Everything else in the recovered rows stays shared:
- AddRef / Release
- ResetRefCount / SetRefCountFromPtr
- GrowPayloadByteCount

So this is the clearest inheritance-like relationship in the family:
- `0x004ba23c` is the live derived table layered on top of `0x004ba220`

## Final-release behavior

Slot `+0x0c = 0x455b80` is the live counterpart to the base table's purecall.
Disassembly shows it:
- acquires lock `0x4cc654`
- temporarily installs base/reset-time table `0x004ba220`
- releases the inner payload object at outer `+0x0c`
- collapses to base refcounted table `0x004b211c`
- pushes the outer object onto free-list `0x4f8408`
- releases the lock

So `Release()` to zero on the live outer object returns it to the **outer-object pool**.

## Why this table matters for current runtime work

This is the outer object family that later receive-side code expects when it does not just want raw
payload bytes.
That is why the late callback84/client raw-`0x38` crash had to be fixed by passing the real local
outer receive/message-ref scaffold rather than a null work item.

In other words:
- `0x004ba208` = inner payload carrier
- `0x004ba23c` = live outer receive/message-ref object that owns/references it

Current source cleanup now keeps the bounded local scaffold closer to that live shape too:
- raw outer front matter `+0x00 .. +0x20` stays primary
- one inline local inner-storage tail begins only after raw `+0x24`
- local outer copies rebind raw `+0x0c` to that inline tail instead of treating a shared_ptr-owned shell as the primary identity
- default packet-agenda read pass-through now preserves the nearer message-ref pointer handoff through agenda `+0x08`
