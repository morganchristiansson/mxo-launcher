# 0x004a9b40 - autodetect dialog object

## Overview

`0x004a9b40` is the concrete vtable installed by `0x401520` for the launcher-owned autodetect dialog used from `CLauncher::InitInstance` when parser gate `0x4d2c64` is set.

Current best identity:

- **autodetect settings dialog (`CDialog`-derived)**

This is the stack object constructed at `0x40b763`, passed through `DoModal`, and later destroyed after the autodetect pre-client branch.

## Evidence

### Constructor installs this vtable

Ctor `0x401520` does:

- `CDialog::CDialog(this, 0x85, parent)`
- `*(this) = 0x004a9b40`
- `*(this + 0x74) = 0`
- loads icon resource `0x83` into `*(this + 0x78)`

That makes `0x004a9b40` the concrete dialog subclass vtable, not plain base `CDialog`.

### Startup uses it as the autodetect gate consumer

`CLauncher::InitInstance` at `0x40b75a` does:

- test launcher-global autodetect gate `0x4d2c64`
- if set, construct this object on the stack with `0x401520`
- call `CDialog::DoModal`
- destroy the object with `0x4012e0`

So this vtable belongs to the launcher-owned autodetect/settings dialog, not a generic utility dialog.

### OnInitDialog launches the helper asynchronously

Virtual `OnInitDialog` is `0x401640`.
That body:

- sets the window icon from `+0x78`
- changes button `0x407` text to `Cancel`
- clears byte `+0x74`
- stores the active dialog pointer in global `0x4d2570`
- starts `_beginthread(0x401590)` and stores the thread handle in `0x4d256c`
- if thread creation fails, falls back to `0x4013c0` to populate the ready UI state immediately

The worker thread at `0x401590`:

- brings the launcher window to the top
- launches `autodetect_settings.exe setopts hide`
- waits up to `60000` ms
- records exit code in `0x4d2568`
- calls `0x4013c0` to populate strings:
  - `Default Settings:`
  - `Detail:`
  - `Memory:`
  - `Continue`

### Close helper is separate from the destructor

The dialog close helper `0x401300` is distinct from destructor `0x4012e0`.

`0x401300`:

- checks byte `+0x74`
- if the dialog is **not** yet ready and worker handle `0x4d256c` is live:
  - terminates the worker thread
  - deletes `options.cfg`
- ends the dialog
- clears active dialog pointer `0x4d2570`

`0x4012e0` only:

- restores vtable `0x004a9b40`
- calls `CDialog::~CDialog`

So earlier claims that `0x4012e0` itself deletes `options.cfg` were incorrect.

## Confidence

High for:

- `0x004a9b40` being the autodetect dialog vtable
- ctor `0x401520`
- dtor `0x4012e0`
- `OnInitDialog` at `0x401640`
- worker thread proc `0x401590`
- result UI helper `0x4013c0`
- close helper `0x401300`
- field `+0x74` as the ready/not-ready byte
- field `+0x78` as icon handle

Medium for:

- the exact identity of unresolved inherited `CDialog` slots
- whether any additional close/message handlers should be named from the remaining raw entries
