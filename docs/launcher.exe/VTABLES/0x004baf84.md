## `Parse` behavior (`0x469bf0`)

Current high-confidence behavior from direct decompilation **and assembly**:

- accepts:
  - an optional read-operation buffer fragment
  - an out-pointer for the completed parsed-packet work item
- current best fragment-object shape on that path:
  - worker-thread receive vtable = `0x004b2300`
  - worker-thread receive allocation size = `0x100c`
  - `+0x04` = interlocked refcount
  - dword `+0x08` = byte count
  - bytes begin at `+0x0c`
  - vtable `+0x00` = deleting-dtor-style entry
  - vtable `+0x04` = no-arg AddRef / retain on the fragment object itself
  - vtable `+0x08` = no-arg Release on the fragment object itself
  - vtable `+0x10` = reset refcount to zero
  - vtable `+0x14` = set refcount from pointed-to value

### Call shape and ownership

The first receive call is now tightly confirmed as:

- `CLTTCPConnection::OnReceive` prepares `(readOperationFragment, &completedPacketWorkItem)`
- then calls `readOperationFragment->+0x04()`
- then calls `parser->Parse(readOperationFragment, &completedPacketWorkItem)`

Later drain calls are explicitly:

- `parser->Parse(0, &completedPacketWorkItem)`

Inside `Parse` itself, the same stack pattern appears again:

- parser first calls `readOperationFragment->+0x04()`
- then immediately calls `CParsedPacketWorkItem_AppendFragment(currentWorkItem, readOperationFragment)`
- that proves the apparent stack argument beside the retain call belongs to `AppendFragment`, not
  to the fragment virtual

Ownership meaning now narrows too:

- `Parse` takes a transient reference on the incoming fragment
- `CParsedPacketWorkItem_AppendFragment` retains any fragment that becomes part of the parser-owned
  work item
- `Parse` then calls fragment `+0x08` on all exits to drop its transient reference
- `CLTTCPConnection::OnReceive` finally calls fragment `+0x08` once more to drop the outer
  callback-held reference

### Framing behavior

`Parse`:

- accumulates stream fragments into the parser-owned current work item at parser `+0x14`
- decodes the 1-byte / 2-byte variable-length prefix format
- rejects malformed prefixes and oversized packets
  - returns `0x700000b` on invalid/oversized framing
- returns `0x7000000` when more data is still needed
- returns `0` and writes a completed `CParsedPacketWorkItem` to the out slot when a full framed
  packet is available

## New clarification: parser output object is both assembly state and completed packet

This is the key narrowed result from the current pass.

### During assembly

The parser owns a current `CParsedPacketWorkItem` at parser `+0x14`.
Incoming fragments are retained into that object via `CParsedPacketWorkItem_AppendFragment`.

### At emit time

When the decoded packet-body length at work-item `+0x28` is `<= parser+0x0c` unread buffered bytes,
`Parse`:

- writes work-item `+0x24 = parser+0x08`
  - i.e. the cursor pointer where the packet body begins in the retained fragment backing
- advances parser cursor state through
  - `0x472660 = CVariableLengthPrefixedTCPStreamParser_AdvanceBufferedCursor`
- returns the current work item through `outCompletedPacketWorkItem`
- then calls parser virtual `+0x0c` / `CVariableLengthPrefixedTCPStreamParser_ResetAfterPacket`

### After emit

`CVariableLengthPrefixedTCPStreamParser_ResetAfterPacket` (`0x4725c0`) now proves the object-family
reuse boundary:

- saves the just-emitted work item from parser `+0x14`
- allocates a **fresh** replacement work item through parser virtual `+0x10`
  - `0x469b40 -> 0x435db0 -> 0x435090`
- releases parser `+0x04` current-fragment state
- clears parser `+0x10`
- if unread buffered bytes remain:
  - gets the old work item’s tail fragment via `CParsedPacketWorkItem_GetTailFragment`
  - stores/retains that tail fragment back at parser `+0x04`
  - appends that tail fragment into the fresh replacement work item
  - sets fresh replacement work-item `+0x24 = parser+0x08`

That means the parser-emitted object is:

- **a completed packet with retained fragment backing**, and
- **the same class family as the parser’s reusable assembly-state object**

So the right answer to the old either/or question is now:

- **both, depending on phase**

## Why this matters for `CLTTCPConnection::OnReceive`

This sharply narrows the old vague “poll helper at `+0x6c`” reading.

`0x449d40` is not polling an anonymous socket helper there.
It is driving a concrete parser object:

- connection `+0x6c` = `CVariableLengthPrefixedTCPStreamParser`
- `OnReceive` repeatedly asks that parser for completed framed packets
- each yielded `CParsedPacketWorkItem` is then queued into the engine through `0x436820`

And the queued object is now understood more precisely than before:

- not a detached raw byte blob
- not only a one-shot packet allocation
- but a fragment-backed parsed-packet object family that also serves as the parser’s in-progress
  assembly state across packet boundaries
