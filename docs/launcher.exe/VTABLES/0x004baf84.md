# VTable `0x004baf84` - `CVariableLengthPrefixedTCPStreamParser`

## High-confidence identity

This vtable is the stream parser object stored at connection `+0x6c` on the `CLTTCPConnection` family.

Evidence:

- `CLTTCPConnection_ctor` (`0x44aad0`) stores its third ctor arg into connection `+0x6c`
- `FUN_00448b40` obtains that object via:
  - `CVariableLengthPrefixedTCPStreamParser_StaticAllocate` (`0x469f50`)
  - `CVariableLengthPrefixedTCPStreamParser_ctor` (`0x469b20`)
- `CLTTCPConnection::OnReceive` (`0x449d40`) calls the helper at connection `+0x6c`
- `0x469bf0` is string-backed by
  - `CVariableLengthPrefixedTCPStreamParser::Parse(): ...`

## `Parse` behavior (`0x469bf0`)

Current high-confidence behavior from direct decompilation **and assembly**:

- accepts an optional read-operation buffer fragment and an out-pointer for the completed packet
  work item
- current best fragment-object shape on that path:
  - dword `+0x08` = byte count
  - bytes begin at `+0x0c`
  - vtable `+0x04` = no-arg AddRef / retain on the fragment object itself
  - vtable `+0x08` = no-arg Release on the fragment object itself
- exact first-call ABI now narrows cleanly:
  - `CLTTCPConnection::OnReceive` prepares `(readOperationFragment, &completedPacketWorkItem)` on the
    stack
  - then calls `readOperationFragment->+0x04()`
  - because that retain call does **not** consume the prepared stack args, the immediately following
    virtual on connection `+0x6c` is exactly:
    - `parser->Parse(readOperationFragment, &completedPacketWorkItem)`
- later drain calls are the explicit simpler shape:
  - `parser->Parse(0, &completedPacketWorkItem)`
- inside `Parse` itself, the same stack pattern appears again:
  - parser first calls `readOperationFragment->+0x04()`
  - then immediately calls `CParsedPacketWorkItem_AppendFragment(workItem, readOperationFragment)`
  - that proves the apparent stack argument beside the retain call belongs to `AppendFragment`, not
    to the fragment virtual
- ownership meaning now narrows too:
  - `Parse` takes a transient reference on the incoming fragment
  - `CParsedPacketWorkItem_AppendFragment` retains any fragment that becomes part of the completed
    work item
  - `Parse` then calls fragment `+0x08` on all exit paths to drop its transient reference
  - `CLTTCPConnection::OnReceive` finally calls fragment `+0x08` once more to drop the outer
    callback-held reference
- accumulates stream fragments into the parser-owned assembly buffer
- decodes the 1-byte / 2-byte variable-length prefix format
- rejects malformed prefixes and oversized packets
  - returns `0x700000b` on invalid/oversized framing
- returns `0x7000000` when more data is still needed
- returns `0` and writes a completed packet object to the out slot when a full framed packet is
  available
- after emitting one packet, calls `CVariableLengthPrefixedTCPStreamParser_ResetAfterPacket` so
  later calls can continue draining buffered stream data

## Why this matters for `CLTTCPConnection::OnReceive`

This sharply narrows the old vague "poll helper at `+0x6c`" reading.

`0x449d40` is not polling an anonymous socket helper there.
It is driving a concrete parser object:

- connection `+0x6c` = `CVariableLengthPrefixedTCPStreamParser`
- `OnReceive` repeatedly asks that parser for completed framed packets
- each yielded packet object is then queued into the engine through `0x436820`

New tight link to the existing queue-work-item RE:

- parser helper `0x469b40` allocates the completed packet object via:
  - `0x435db0` allocation
  - `0x435090` constructor
- that constructor seeds vtable `0x4b3e08` on a `0x2c` object
- this is the same `0x2c` work-item family already seen in earlier queue producer analysis

So the parser is not just returning arbitrary bytes.
It is materializing a concrete queueable work-item object family that `OnReceive` can immediately enqueue.

That gives a much tighter source-side target for the current `CLTTCPConnection::ParseReadOperationFragmentScaffold(...)` scaffold.
