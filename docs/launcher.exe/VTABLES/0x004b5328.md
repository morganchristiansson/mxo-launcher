# 0x004b5328 - CLTLoginMediatorSlotRecord

## Overview

Current best identity:
- concrete **per-character mediator slot record object** stored under the owner
  `0x4f78b8 + 0x688[index]` table
- broader writer `launcher.exe:0x43f300 = CLTLoginState_AuthenticatePending_AuthMessageDispatch`
  allocates/builds this `0x1c`-byte class from auth-character data
- later narrower helper10 path `launcher.exe:0x4401a0` reuses the same class for selected-slot
  writeback/refresh
- used together with the parallel owner families at:
  - `+0x818` = per-character route-host string triples
  - `+0xd84` = separate world-descriptor table used to seed `+0x818` by world-id matching

This older doc's `CLTCharacter` name is now too strong and too narrow.
The stronger evidence-backed read is that this is a **launcher-owned mediator slot record**, not yet a settled gameplay-side class identity.

## Evidence chain

### Allocation / construction
From `launcher.exe:0x43f300 = CLTLoginState_AuthenticatePending_AuthMessageDispatch`:
- allocates `0x1c` bytes via `0x403260(0x1c)`
- builds the object from auth-character data via `0x4398b0` / `0x43c2c0`
- stores it at owner `+0x688[characterIndex]`
- validates payload byte `+0x0b` as character status, forcing invalid values to `7`
- then joins this record's world id against the separate `+0xd84` world-descriptor table to seed
  the parallel `+0x818` route-host string slot

Later `launcher.exe:0x4401a0 = CLTLoginMediator_Helper10_HandleAuthReply` also allocates the same
class at `+0x688[currentSlot]`, copies owner `+0x108` through `0x43aa80`, and writes additional
selected-slot fields into the payload.

### Current-slot table accessors
Recovered owner-vtable consumers:
- owner vtable `+0x40` / `0x41f2e0`
  - returns `owner + 0x688[index]`
- owner vtable `+0x44` / inline thunk at `0x41f300`
  - loads owner byte `+0xcc8`
  - forwards to `+0x40`
- owner vtable `+0xdc` / `0x41b220`
  - returns `record->+0x14`

So this object is part of a real, reusable owner-side **character-slot** interface family.

## Key methods

### `0x004398b0` - `CLTLoginMediatorSlotRecord_Initialize`
Initializes the `0x1c`-byte object:
- sets vtable `0x004b5328`
- prepares/owns an inline payload buffer
- zeroes:
  - payload byte `+0x00`
  - payload word `+0x01`
  - payload dwords `+0x03`, `+0x07`
  - payload byte `+0x0b`
  - payload word `+0x0c`

This is the clearest constructor/init anchor for the class.

### `0x0043aa80` - `CLTLoginMediatorSlotRecord_CopyHeapStringFromCString`
If object word `+0x18 == 0`, it:
- sizes the incoming C string
- reserves space through `0x43a230`
- copies the text into object `+0x14`
- NUL-terminates it

On the auth-success path, helper10 feeds this from owner `+0x108`.

### `0x0043d430` - `CLTLoginMediatorSlotRecord_CopyInlineNameToString`
Reads the object's payload pointer at `+0x10`, then copies the NUL-terminated string at:
- `payload + 0x03`
into an external 3-dword string object.

This is the strongest current read for how owner helper10 copies text out of the upstream `+0xd84[index]` descriptor family into owner `+0x818[currentSlot]`.

### `0x00439940` - `CLTLoginMediatorSlotRecord_ResetPayloadForSourceDescriptor`
Uses the upstream descriptor object at `object->+0x08` to:
- compute a payload-dependent span size from byte `payload+0x0d`
- move/resize the internal payload buffer
- then zero the record fields at `payload + 0x00/+0x01/+0x03/+0x07/+0x0b/+0x0c`

This is good evidence that the object owns a small **typed inline record payload**, not just one string.

### `0x0043dc80` - `CLTLoginMediatorSlotRecord_AppendDebugString`
Formats human-readable fields:
- `Name:"..."`
- `GlobalCharacterId:` from payload `+0x03/+0x07`
- `Status:` from payload `+0x0b`
- `WorldId:` from payload `+0x0c`

This strongly confirms the payload interpretation above.

## Practical implication for the launcher reimplementation

This class is the best current concrete source anchor for the post-auth **character-slot** family written by:
- `launcher.exe:0x43f300 = CLTLoginState_AuthenticatePending_AuthMessageDispatch`
- `launcher.exe:0x4401a0 = CLTLoginMediator_Helper10_HandleAuthReply`

To make the live launch branch faithful, source and docs should treat this object as part of the owner-side slot machinery together with:
- `+0x688` character-slot table
- `+0x818` per-character route-host string table
- `+0xd84` upstream world-descriptor table

Current highest-value practical read:
- `+0xd84` supplies world metadata/name
- `+0x688` supplies character id/status/world-id
- `+0x818` is the join output the later state-8 margin path actually consumes

That family is now a higher-value blocker for launch progress than the older incorrect world-name override path.
