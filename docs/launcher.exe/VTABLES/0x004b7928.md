## Class Identification

**This vtable is the shared `CMessageConnection` base table**, not a distinct inferred `CAuthConnection` leaf.

### Evidence:
- `0x448b40` is already recovered as `CMessageConnection_ctor` and installs vtable `0x004b7928`
- `0x4490c0` is string-backed as **`CMessageConnection::OnOperationCompleted`**
- `0x448cf0` is string-backed as **`CMessageConnection::SendPacket`**

- later derived tables (`0x004b62b8`, `0x004b64a8`, `0x004aff38`, and startup leaf `0x004afef0`) reuse this shared surface

## Purpose
**`CMessageConnection`** is the shared message-oriented TCP layer above `CLTTCPConnection`:
1. shared send path via `CMessageConnection::SendPacket`
2. shared receive/completion path via `CMessageConnection::OnOperationCompleted`
3. optional packet-agenda / transform plumbing rooted at `+0x74`
4. optional completion-helper objects at `+0x7c` / `+0x80`
5. common teardown via `0x448c30` / `0x449090`
6. current Ghidra layout correction on the active `0x4490c0` path:
   - OOAnalyzer `CMessageConnection_0x4b7928` should keep a real `vftptr_0x0` at `+0x00`
   - inherited connection fields needed by this callback should remain visible at:
     - `engine10`
     - `remoteEndpoint24`
     - `parser6c`
   - treating the whole vtable as an inline struct member breaks `0x4490c0` decompilation by
     hiding the inherited `+0x24` endpoint copy behind bogus `&(this->vtable...).slot_36`-style
     expressions instead of the real `LTTCPEndpointKey` storage

## Current narrowed `0x4490c0` type-3 parsed-packet copy path

A newer focused pass over `CMessageConnection::OnOperationCompleted` now makes the first useful
consumer-side step more concrete than the older generic “operation completed” summary.

Static-RE-backed points from `0x4490c0`:

- `workItem+0x04` is the first dispatch key
- only work types `1`, `2`, and `3` are directly handled there
  - type `1` = close-completion helper branch
  - type `2` = connect-completion helper branch
  - every other non-type-3 work item falls straight back out of base `0x4490c0`
- type `3` is the parsed-packet path fed from `CLTTCPConnection::OnReceive -> 0x436820`
- on that path, `0x4490c0` reads:
  - `CParsedPacketWorkItem.currentCursor24`
  - `CParsedPacketWorkItem.assembledByteCount28`
- the first copy span is computed from the first retained fragment and `currentCursor24`
- later spans walk subsequent retained fragments until the assembled packet-body byte count is
  satisfied
- if extra retained buffers remain after the requested body bytes were copied, the function reaches
  the string-backed:
  - `Unused buffers were attached to CLTTCPReadOperation from %d.%d.%d.%d:%d.`
- if `assembledByteCount28 > 0x1000`, the function logs the illegal packet and closes the
  connection before later dispatch work
