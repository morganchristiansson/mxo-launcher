## Key specialized methods
- `0x004393f0` is strong evidence that slot 2 is genuinely virtual here: it explicitly falls back to the shared `0x00438df0`, but on its special case it calls `(*(this->vtable)[2])(this+4)`.
- `0x00439300` is now re-read from both decompilation and disassembly as a very specific cached-upstream dispatcher:
  - if `this+4` is null, it stores the incoming argument there first
  - then it calls the cached upstream/helper object's vtable `+0x18`
  - case split from the resulting code:
    - case `6`:
      - call owner vtable `+0x10c`
      - use the first dword of the returned object
      - call `0x0041e500`
    - cases `7`, `8`, `0x0d`:
      - read owner byte `+0xcc8`
      - call owner vtable `+0xe0(slot, 0)`
      - call `0x0041e500`
    - case `10`:
      - read owner dword `+0x12c`
      - newer `0x41c3c0` + `0x4401a0` tightening now makes that field's role narrower:
        current best read is a selected world-descriptor index / selector, not a direct world id
      - call owner vtable `+0xfc(value, 0)`
      - call `0x0041e500`
    - default:
      - read owner dword `+0x104`
      - if it is not `-1`, call owner vtable `+0xfc(value)`
      - only if that result is non-null does it call `0x0041e500`
- ownership/source consequence to keep explicit:

## Composition notes
- This is one of the clearest **derived override** cases in Family B because slot 2 explicitly falls back to the shared base implementation when its own special case does not apply.
- Together with `0x004b5064` and `0x004b50dc`, it defines the B1 sub-branch that customizes slot 2 instead of keeping `0x00438df0` unchanged.
