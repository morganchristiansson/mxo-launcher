# 0x004b75e4 - AuthBootstrap680Raw08PublicKeyWorker leaf

## Overview
Concrete leaf vtable for the owner `+0x680 -> +0xa8` reply-public-key worker rebuilt by:
- `0x447780 = AuthBootstrap680_RebuildReplyPublicKeyWorkers`
- ctor `0x447120 = AuthBootstrap680Raw08PublicKeyWorker_ConstructFromReplyPublicKey`

Constructor-state note:
- `0x447120` first installs intermediate 11-slot vtable `0x004b74a8`
- then rewrites the primary vfptr to this final leaf `0x004b75e4`
- so `0x004b74a8` and `0x004b75e4` should be read as two construction phases of the same Crypto++
  encryptor family, not as unrelated launcher-local worker classes

Current source mirrors:
- `matrixstaging/game/src/libltclientlogin/authbootstrap680_internal.h`
  - `AuthBootstrap680Raw08PublicKeyWorkerA8Sketch`
  - `AuthBootstrap680Raw08PerChunkWorker48Sketch`

High-value role now closed better than before:
- holds the parsed raw-`0x07` reply RSA public key at outer `+0x14/+0x28`
- `0x4474f0` consumes it through:
  - `0x468ea0 = AuthBootstrap680Raw08PublicKeyWorker_QueryEncryptedOutputLength`
  - `0x468f00 = AuthBootstrap680Raw08PublicKeyWorker_EncryptIntoPacketBuilder`
- `0x468f00` iterates plaintext in chunks and advances the output pointer by one ciphertext block per chunk

## Key call-shape facts
### `0x468ea0`
`0x468ea0` computes:
- `ciphertextBlockBytes * ceil(plaintextByteCount / plaintextChunkBytes)`

where:
- ciphertext block bytes come from worker vtable `+0x24 -> 0x41f090 -> this+0x0c -> modulus`
  and then flow through `0x45a400`, so the launcher-side byte count is derived from the modulus
  bit length rather than from a generic encryptor-side constant
- plaintext chunk bytes come from the helper family behind outer `this+4/+8`

### `0x468f00`
Disassembly now tightens the per-chunk call shape materially:
- `0x468f00` queries ciphertext block bytes from vtable `+0x24`
- it re-queries the plaintext chunk bound each loop from the helper family behind `this+4/+8`
- it pushes **four** stack args into worker vtable `+0x1c`
- `0x468280` returns with `ret 0x10`

That matters because the decompiler undercounts the `+0x1c` arguments unless checked against assembly.

Current best outer arg mapping from `0x468f00` is:
- caller arg `+0x10` = current plaintext pointer (advanced by chunk size each iteration)
- caller arg `+0x14` = remaining plaintext byte count
- caller arg `+0x18` = current ciphertext/output pointer (advanced by one ciphertext block per iteration)
- one additional stable caller arg at `+0x0c` is forwarded unchanged into every `+0x1c` call

## Temporary helper allocated by `+0x20`
`0x4382c0` allocates a concrete `0x48`-byte helper and constructs it through:
- `0x438120 = AuthBootstrap680Raw08PerChunkWorker_Construct`
- final vtable `0x004b4478`

Stronger current bounded layout:
- `0x438120` first runs `0x453570(this, param3)`
  - that seeds inherited helper front matter and stores ctor arg3 at helper `+0x08`
- `+0x14` is not a flat inline `0x100` scratch array
  - it is a constructed `0x1c` node-buffer/output-buffer helper from
    `0x454f10(this+0x14, 0x100)`
  - sibling virtuals query strings `"NodeSize"` and `"OutputBuffer"`
  - that subobject owns heap-backed node pointers and has its own release path
- helper vtable `+0x1c / 0x437870` releases the constructed `+0x14` subobject through `0x455470`
- `+0x30` = ctor arg1 copied verbatim by `0x438120`
- `+0x34` = ctor arg2 / owning raw-`0x08` worker pointer copied verbatim by `0x438120`
- `+0x40/+0x44` = ctor-zeroed tail dwords
- negative result worth keeping explicit: active encrypt body `0x468280` does **not** read
  `+0x30/+0x34/+0x40/+0x44`; current evidence says those belong to sibling virtuals on the same
  helper family, not to the hot chunk body itself

The exact inherited filter/transform family on this `0x48` helper is still unresolved.

## What `0x468280` now proves
Current stronger read of the per-chunk body:
- it allocates a scratch buffer sized from the modulus bit count as `((modulusBits - 1) + 7) >> 3`
  using the public-key family at `this+8`
- it fetches another helper object from the same `this+8` family and calls that helper's vtable `+0x08`
  with:
  - the forwarded stable caller arg
  - current plaintext pointer
  - current chunk byte count
  - scratch buffer pointer
  - `(modulusBitCount - 1)`
- it then wraps the scratch buffer through `0x461ee0`
- it converts the caller output span into another tiny sink/helper through `0x460980`
- finally it pushes the wrapped scratch buffer into a deeper helper path that writes into that
  caller-provided output sink, then frees the scratch buffer

So the source-side OAEP chunk loop is still only a bounded stand-in for this helper-object stack; it is not a full structural match yet.

## Current fidelity boundary
Source now treats this as a concrete class-shaped leaf and routes raw-`0x08` blob encryption through a thin worker method mirroring the recovered `0x468ea0/0x468f00` chunk loop.
The currently important construction nuance is now closed more tightly too:
- `0x004b74a8` = ctor-state vtable
- `0x004b75e4` = final leaf vtable

But the deeper helper/temporary-worker inheritance stack under:
- `0x004b7610`
- `0x004b7138`
- `0x004b67a0`
- `0x004b4478`

is still only partially typed. Keep future work narrow and anchored to the actual send-time call shape rather than inventing a generic crypto framework.
