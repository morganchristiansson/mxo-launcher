# 0x004b533c - CLTLoginMediatorWorldDescriptor

## Overview

Current best identity:
- concrete `0x14`-byte **world-descriptor object** allocated by
  `launcher.exe:0x43f300 = CLTLoginState_AuthenticatePending_AuthMessageDispatch`
- stored under the owner `0x4f78b8 + 0xd84[index]` table
- this table is built from auth-world data before the sibling character-slot table at:
  - `+0x688` = `0x004b5328` character-slot records
  - `+0x818` = per-character route-host string triples

The stronger evidence-backed read is that `+0xd84` is **not** the same family as `+0x688`.
It is the upstream **world table** that later seeds `+0x818` by world-id matching.

## Evidence chain

### Allocation / construction
From `launcher.exe:0x43f300 = CLTLoginState_AuthenticatePending_AuthMessageDispatch`:
- allocates `0x14` bytes via `0x403260(0x14)`
- initializes the object via `0x43c310`
- stores it under owner `+0xd84[index]`
- validates:
  - payload byte `+0x17` = world status
  - payload byte `+0x18` = world type
- on invalid values, logs and forces them to `0`

### Downstream consumers
Recovered owner-vtable readers:
- owner vtable `+0xfc` / `0x41b2e0`
  - returns `descriptor->payload + 3`
- owner vtable `+0x100` / `0x41b320`
  - returns payload byte `+0x18`
- owner vtable `+0x104` / `0x41b360`
  - returns payload byte `+0x19` (low byte of server-version dword)
- owner vtable `+0x108` / `0x41b3a0`
  - returns `(payload + 0x1f) & 0xf` when in `1..3`

### How it seeds `+0x688` and `+0x818`
Still from `0x43f300`:
- after the world-descriptor table is built, the launcher builds `+0x688` from auth-character data
- each character record's `worldId` (`payload + 0x0c` in the `0x004b5328` family) is matched
  against each world descriptor's `worldId` (`payload + 0x01` here)
- on match, the launcher copies this descriptor's inline name (`payload + 0x03`) into the
  parallel `+0x818` string-triple slot

So the best current relation is:
- `+0xd84` = world descriptors
- `+0x688` = character-slot records
- `+0x818` = per-character route/world-name strings derived from the world descriptors

## Key methods

### `0x0043c310` - `CLTLoginMediatorWorldDescriptor_InitializeFromTempRecord`
Copies the upstream temp/source object into the heap world-descriptor object:
- sets vtable `0x004b533c`
- copies shared base fields `+0x04/+0x08/+0x0c/+0x10`
- retains the referenced backing object at `+0x08`

### `0x00439a70` - `CLTLoginMediatorWorldDescriptor_ResetPayload`
Rebuilds the descriptor payload span from the upstream source object:
- computes payload size from byte `payload+0x0d`
- updates the internal payload pointer
- zeroes:
  - payload byte `+0x00`
  - payload word `+0x01`
  - payload dword `+0x03`
  - payload dword `+0x07`
  - object fields `+0x14/+0x18`

This is the world-descriptor sibling of the already-documented `0x00439940`
slot-record reset path.

### `0x0043ded0` - `CLTLoginMediatorWorldDescriptor_AppendDebugString`
Formats human-readable world fields:
- `WorldId:` from payload `+0x01`
- `Name:"..."` from payload `+0x03`
- `Status:` from payload `+0x17`
- `Type:` from payload `+0x18`
- `ServerVersion:` from payload `+0x19`
- `ServerLanguage:` from payload `+0x1d`
- `Private:` from payload `+0x1e`
- `PopulationLevels:` from payload `+0x1f`

This is the strongest current proof that the `+0xd84` family is the launcher's auth-world table.

## Practical implication for the launcher reimplementation

For the live launch path, source/docs should now treat `+0xd84` as the canonical upstream
world-descriptor table that feeds the character-oriented post-auth families:
- `+0x688`
- `+0x818`

This is the key bridge needed to stop the state-8 margin path from depending on old fallback-only
world-name state.
