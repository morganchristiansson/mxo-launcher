# VTable `0x004ba208` - inner payload-storage object for the `CMessageConnectionMessage` family

This table is the **inner `0x100c` payload-storage object** allocated inside
`0x455bd0 = CMessageConnectionMessage_ResetForPacketBuilder` and stored through the outer object at
`+0x0c`.

It is not the live outer receive/message-ref object itself.
That outer family uses:
- `0x004ba220` = reset-time/base outer table
- `0x004ba23c` = live outer table

## Object layout this table belongs to

Current best raw layout from `0x455bd0`:
- `+0x00` = vtable `0x004ba208`
- `+0x04` = refcount dword
- `+0x08` = reserved word initialized to `0x002b`
- `+0x0a/+0x0b` = payload-byte-count header bytes
- `+0x0c .. +0x100b` = inline payload storage

Constructor/reset proof from `0x455bd0`:
- allocates `0x100c`
- stores vtable `0x004ba208`
- writes:
  - `[obj+0x08] = 0x2b`
  - `[obj+0x0a] = 0`
  - `[obj+0x0b] = 0`

Current source cleanup now follows that raw contract more directly too:
- no persistent vector mirror is needed on the receive-side inner scaffold anymore
- source rebuilds payload length directly from raw `+0x0a/+0x0b`
- that decoded length is clamped to `0x1000`, not bit-masked
- any `std::vector` view is now copied on demand from raw `+0x0c..`
- send-side tightening now also treats these same raw bytes as primary truth:
  - `0x448a00` derives final send pointer/size directly from inner `+0x0a/+0x0b/+0x0c..`
  - headerless/send-mode branch in `0x448cf0` conditionally mutates inner `+0x12/+0x16/+0x17`
  - after that branch, `0x448cf0` clears the high bit of the first payload byte at inner `+0x0c`

## Inheritance / family relationship

This looks like a **small refcounted payload-storage leaf** in the same broader family as
`0x004b211c`:
- destructor collapses back to base vtable `0x004b211c`
- refcount field remains at `+0x04`
- reset/set-refcount slots match the shared refcounted helper contract

More specifically:
- `0x004b211c` = common base refcounted family
- `0x004ba208` = inner payload-storage leaf used by the outer message object

It also shares the **interlocked** `AddRef/Release` helper pair (`0x42f850/0x42f860`) seen on the
later read-operation family, so this is not just the plain non-interlocked base table reused
verbatim.

## Final-release behavior

Slot `+0x0c = 0x455ad0` is not a generic pure virtual.
Disassembly shows it:
- acquires lock `0x4cc61c`
- installs base vtable `0x004b211c`
- pushes the object onto free-list `0x4f83f0`
- releases the lock

So when interlocked `Release` drops the refcount to zero, this inner payload object is **returned to
its pool**, not immediately `free()`d.

## Why it matters

This table is the concrete proof that the `CMessageConnectionMessage` family is split into:
1. an **outer refcounted message-ref object**
2. an **inner refcounted payload-storage object** at outer `+0x0c`

That split is exactly the family later consumed by:
- `0x41bc20`
- `0x41bbb0`
- `0x4490c0`
- and the later client-side callback84/raw-`0x38` path
