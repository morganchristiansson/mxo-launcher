# 0x004b5014 - CLTLoginState_AuthenticatePending

## Overview
Family B state object for an earlier auth/bootstrap stage. The object is 8 bytes wide because it caches an upstream pointer at `this+4`.

## Key specialized methods
- `0x00439210` clearly belongs to the state2 login-state handoff into the owner `+0x680`
  bootstrap child:
  - if auth is **not** connected yet, it switches back to helper/state `1`
  - if auth **is** connected, it gathers owner data and calls `AuthBootstrap680_PrepareAndDispatch(...)`
- `0x0043f300` is one of the largest methods in this whole family; it does **not** parse raw auth wire packets by itself.
  Instead it first calls the separate owner `+0x680` child helper `0x448140 = AuthBootstrap680_HandleInboundAuthMessage`, then interprets that helper's return code to:
  - mirror child status into owner `+0x80`
  - build owner-managed world/character arrays
  - normalize invalid status/type values
  - post events `5` / `6` or errors depending on the return code
- Slot 7 (`0x00418150`) is a tiny getter returning `2`, which fits the idea that this helper is an early auth-side state.

## Practical state-flow note
On the current startup path this looks less like “the very first auth state” and more like the
**post-submit login-state handoff into the owner `+0x680` bootstrap child**.

Corrected happy-path WineDbg from a stable EULA attach now proves this early sequence concretely:
- mediator init installs state `0` as the initial current helper
- password submit (`0x41ecd0`) switches `state0 -> state2`
- `0x439210` is entered on state `2` with upstream state `0`
- state `2` then switches `state2 -> state1`
- after the auth-connect side, state `1` switches back `state1 -> state2`
- `0x439210` is re-entered on state `2` with upstream state `1`
- the next switch is `state2 -> state3`

So state `2` is now best read as the handoff point between:
- owner-side password submit
- state `1` auth-connect bringup
- the owner `+0x680` phase-2 auth/bootstrap child
- and the later state `3` selection-context continuation

## Composition notes
- This is best described as an **auth/bootstrap login-state object**.
- Compared with `0x004b4fec`, it sits earlier in the pipeline and performs much heavier bootstrap-side materialization work.
