## Key specialized methods
- `0x00439590` shows the same inheritance-like pattern as `0x004393f0`: it handles a special case itself and otherwise delegates back to the shared `0x00438df0` implementation.
  - current tighter read of that special case:
    - it only takes the local branch when `CLTThreadPerClientTCPEngine_WorkItemHeader_GetWorkType(workItem) == 0x0b`
    - it reads the payload/status dword through
      `CLTThreadPerClientTCPEngine_WorkItemHeader_GetStatusOrPayloadDword` (`0x434d00`)
    - when that dword is non-zero it arms owner byte `+0x2d`
    - then it reads the cached upstream object's phase code and switches to that helper state
- `0x00439520` is the concrete behavior that differentiates this class: it caches an upstream object unless it reports `2` or `4`, probes mediator readiness via `0x004433c0`, and either switches state `2` or runs the `0x41b500` prep/send pair then posts event `0x10`.
  - original-launcher WineDbg confirmation on the active existing-character branch proves this is a
    real happy-path stage, not just a static theory:
    - after the successful state4 slot-2 margin-connect re-entry (`0x4393f0 -> 0x43bd20 -> 0x43b8f0`),
      the run reaches `0x439520`
    - that same call chain then concretely reaches `0x41b500 -> 0x41ce80 -> 0x441f30`
    - so the happy path really does execute the state5 copy/send family before the later restored
      state8 send, rather than skipping directly from state8 into a stable state6-only route
  - replacement-side `2026-03-30` runtime now reaches that same branch live too:
    - state5 slot3 logs `replyCopyShadowStillValid=1`
    - child `+0xf4` is non-null
    - source now keeps the confirmed `0x41b500` prep/send step in its original static-RE split:
      - `0x41b500` is a direct mediator helper body, not a login-mediator vtable row
      - it calls standalone child helper `0x4435f0`
      - `0x4435f0` first calls connection vtable `+0x44 / 0x41ce80` to rebuild margin
        connection `+0x98` from child `+0xf4`
      - `0x4435f0` then calls standalone helper `0x443340`
      - `0x443340` allocates a fresh `0xe0` heap object and stores it at margin connection `+0xa0`
        using child `+0xb0/+0xc4/+0xd8` as constructor inputs
    - `0x41b500` then tail-calls `0x441f30`, so source sends the raw type-1 prefixed packet
      (`01 00 00` + copied `0x136` block, `payloadBytes=0x139`) through the margin connection send
      path before posting event `0x10`
  - immediate new limitation after this milestone:
    - the margin socket returns EOF right after that send on the current replacement path
    - so the active blocker is no longer “state5 cannot see child `+0xf4`”, but whether the copied
      `0x136` block / raw type-1 packet is faithful enough for the server to accept and continue
- Practical code-4 relevance:
  - `0x441850` synthesizes a local type-`0x0b` work-item and routes it back through margin
    connection vtable `+0x10`

  - newer original-launcher WineDbg now confirms that concrete continuation too:
    - after `0x441850 -> 0x41afc0`, current helper vtable is `0x4b5064`

  - so this state5 slot-2 family is the next original continuation seam after the local type-`0x0b`
    work-item, not the slot-6 margin-reply body
