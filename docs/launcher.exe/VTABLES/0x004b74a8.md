# 0x004b74a8 - raw `0x08` worker ctor-state vtable

## Overview

11-slot vtable installed by `0x447120` **before** the final leaf retable to `0x004b75e4`.

Current best interpretation:
- this is an **intermediate constructor-state vtable** for the same Crypto++ OAEP/SHA1 RSA
  encryptor family later finalized as `0x004b75e4`
- it is not the long-term steady-state identity used by child `+0xa8`
- the staged retable is visible directly in `0x447120`

Key constructor sequence from `0x447120`:
1. call base/intermediate ctor `0x446bd0`
2. install primary vtable `0x004b74a8`
3. install secondary/helper slices at `+0x08`, `+0x4c`, and through offset-adjusted subobject
   writes rooted from `+0x04`
4. rewrite primary vtable to final leaf `0x004b75e4`

That shape strongly matches old MSVC multiple-inheritance codegen for Crypto++ template objects.

## Strongest evidence this is ctor-state, not final leaf

### 1. Direct overwrite in `0x447120`
`0x447120` explicitly does:
- `[ESI] = 0x4b74a8`
- later `[ESI] = 0x4b75e4`

So `0x4b74a8` is an in-construction table, while `0x4b75e4` is the final installed table.

### 2. Shared hot crypto entries
The `0x4b74a8` and `0x4b75e4` tables share the same operational encrypt slots:
- `+0x1c = 0x468280`
- `+0x20 = 0x4382c0`
- `+0x24/+0x28 = 0x41f090`

That strongly suggests both tables belong to the **same encryptor family** rather than to unrelated
launcher-local helpers.

### 3. Destructor / thunk pairing
The constructor also installs thunk pointers later consumed by:
- `0x446d80` → calls `~cls_0x4b74a8((this-0x50), flag)`
- `0x4471f0` → `sub ecx, 0x50 ; jmp 0x447880`

Those are classic adjustor-thunk patterns for non-primary base slices.

## Current best class-equivalent reading

This table is best treated as an **intermediate `CryptoPP::RSAES_OAEP_SHA_Encryptor` ctor-state
vtable**, with the final steady-state leaf at `0x004b75e4`.

Put differently:
- `0x004b74a8` = in-construction phase of the raw `0x08` public-key worker
- `0x004b75e4` = final leaf used after ctor completion
