# 0x004b508c - CLTLoginState_State6

## Overview
Family B concrete helper that sends a larger margin packet and then handles the follow-up reply. Allocated as an 8-byte object with two small state bytes.

## Key specialized methods
- `0x0043b8f0` is the outbound step: after mediator/auth checks it fills a packet with several fixed constants plus current mediator values, sends it to margin, and posts event `0x11`.
  - newer original-launcher WineDbg on the active existing-character branch now fixes this method's timing more tightly:
    - it is reached immediately after the post-connect state8 re-entry (`0x4393f0 -> 0x43bd20 -> 0x43b8f0`)
    - on that first pass owner byte `+0xf14` is still `0`
    - `0x41b4b0` is already true there, but `0x41b4d0` then fails and `0x43b8f0` immediately switches to helper/state `5`
    - later, after state5 slot-3 and the local type-`0x0b` slot-2 continuation, the run returns to `0x43b8f0` again through `0x4395de`
  - practical consequence: the existing-character happy path does include state6 slot 3, but not as a one-shot direct bridge to the final restored state8 send
- `0x00440780` is the big differentiator for this object. On opcode `7` it builds a derived buffer using `client.dll` and the current module path; on opcode `9` it updates owner fields, pushes multiple items through owner slot `+0x190`, and then switches state based on the cached upstream object.
  - newer `2026-03-21` tightening now bounds the opcode-`9` reply layout itself much better:
    - `0x0043a0b0 / 0x0043a060` build the reply view
    - `0x0043c950` in launcher.exe and `0x6253f000` in client.dll are the two current
      `"UDPSessionSecret:"` string users
    - that original debug-printer family labels the parsed opcode-`9` fields as:
      - `+0x01` = `Status`
      - `+0x05` = `GoHereAddr`
      - `+0x09` = `UDPSessionSecret`
      - `+0x0d` = offset to `MetrIds` array header `(u16 count, then u16 ids...)`
    - open-server/proxy `MS_ConnectReply` mirrors place the changing session id in that same wire slot
    - current best cross-checked read is therefore:
      - parsed reply `+0x09` = opcode-`9` `UDPSessionSecret` / session-id dword
  - that same pass also answers the long-running owner `+0xf18` question positively:
    - on the opcode-`9` success side it writes:
      - owner byte `+0xf14 = 1`
      - owner dword `+0xf18 = parsedReply(+0x09)`
    - concrete assembly at `0x440ab9..0x440ac9`:
      - `mov eax,[0x004f78b8]`
      - `mov edx,[edi+0x9]`
      - `add eax,0xf14`
      - `mov [eax+4],edx`
      - `mov byte ptr [eax],1`
    - important split to keep explicit:
      - parsed reply `+0x09` feeds owner `+0xf18`
      - the immediate next helper-state target does **not** come from that field; `0x440acc..0x440ae0`
        reloads state6 `this`, reads cached upstream object `this+4`, and calls its vtable `+0x18`
    - practical consequence: this state6 slot-6 body is the first isolated real non-init launcher writer for owner `+0xf18`, and it lands before state8 slot-6 entry `0x43f930`
    - newer original-launcher WineDbg also confirms the later visible effect on the active branch:
      - `0x440780` is reached before the restored state8 sender returns
      - the later restored `0x43bd20` stop then shows owner byte `+0xf14 == 1`
      - and owner dword `+0xf18` already non-zero
      - caller chain there is `0x440ae5 -> 0x43bd20`, matching the static read that state6 slot-6 restores the cached upstream helper and returns to state8 slot 3
    - replacement go/no-go stays narrow:
      - do **not** synthesize `+0xf18` outside this writer path
      - a future faithful source-owned mirror is justified only on state6 opcode-`9` success, sourcing the original `UDPSessionSecret` / session-id field rather than a placeholder value
- Slot 7 (`0x00438c70`) returns `6`.

## Composition notes
- This is a very concrete login-state leaf: it owns both an outbound packet format and a complex reply parser.
- Its object layout (8 bytes with extra bytes reset in the dispatch-table init) matches the later fragment-collecting helpers such as `0x004b5104` and `0x004b5154`.
