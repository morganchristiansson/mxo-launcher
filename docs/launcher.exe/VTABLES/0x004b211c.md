# VTable `0x004b211c` - shared low-level refcounted base contract

This is the immediate base vtable that `CLTTCPReadOperation_dtor` installs before optionally
freeing the derived object.

A later cross-family pass also shows the same base contract reappearing under the message-ref /
payload-storage family (`0x004ba208`, `0x004ba220`, `0x004ba23c`).
So this doc should now be read as a **shared low-level refcounted base contract**, not only as a
fragment-only semantic class.

## Current best interpretation

This looks like a small non-interlocked base contract reused by at least two higher-level families:

- the later `CLTTCPReadOperation` vtable at `0x004b2300`
- the message payload / outer message-ref teardown chain rooted through
  `0x004ba208`, `0x004ba220`, and `0x004ba23c`

Shared traits visible here:

- same field focus:
  - `+0x04` = refcount
- same release-to-vtable-`+0x0c` pattern
- same deleting-dtor-style slot `+0x00`
- same reset / set-refcount utility slots at `+0x10` / `+0x14`

Key derived/base difference recovered so far:
- base `0x004b211c` mutates `+0x04` with plain integer ops
- derived `0x004b2300` uses interlocked Win32 ops on the same field

So the current best read is:
- `0x004b211c` = shared low-level refcounted base contract
- `0x004b2300` = interlocked / TCP-read-operation derived family actually seen on the live worker
  receive path
- `0x004ba208` / `0x004ba220` / `0x004ba23c` = other derived users of the same low-level base
  contract on the message-object side
