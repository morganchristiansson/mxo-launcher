# VTable `0x004b3e20` - `CMessageConnectionCompletionHelper`

## Class identification

This `0x24` object is the small **event + critical-section completion helper** constructed by
`CMessageConnection_ctor` and stored at connection `+0x7c` / `+0x80` when the
`allocateCompletionHelpers` flag is enabled.

Current best evidence:
- `0x436080` constructs the object in-place
- ctor installs a transient base vtable at `0x004b3e18`, initializes the embedded critical section,
  then switches to the live vtable at `0x004b3e20`
- ctor creates an auto-reset event and stores the handle at `+0x20`
- `CMessageConnection_OnOperationCompleted` uses the helper on work types `1` and `2`
- `0x448af0` waits on the `+0x80` helper through vtable row 1
- `CMessageConnection_dtor` / `0x448c30` manually closes the event, deletes the critical section,
  and frees the helper

## Recovered layout

`0x436080` gives the current high-confidence field map:

| Offset | Meaning |
|---|---|
| `+0x00` | vtable pointer |
| `+0x04` | embedded lock-helper vtable pointer (`0x4add70` family) |
| `+0x08` | embedded `CRITICAL_SECTION` storage |
| `+0x20` | event handle from `CreateEventA(0, 0, 0, 0)` |

## Methods

### `0x435f90 = CMessageConnectionCompletionHelper_SignalEvent`

Decompile shape:
- `SetEvent(this->eventHandle20)`
- returns `0` on success, `1` on failure

This is the vtable row used by `CMessageConnection_OnOperationCompleted` after first entering the
helper's embedded lock.

### `0x435fa0 = CMessageConnectionCompletionHelper_LeaveLockAndWaitForEvent`

Decompile shape:
- leaves the embedded lock
- waits on `eventHandle20`
- re-enters the embedded lock on `WAIT_OBJECT_0` and `WAIT_TIMEOUT`
- returns:
  - `0` on signaled
  - `3` on timeout
  - `1` on failure

This is the wait-style helper used from `0x448af0` on the `closeCompletionHelper80` path.

## Construction / ownership notes

### `0x436080 = CMessageConnectionCompletionHelper_ctor`

Current ctor behavior:
1. install transient vtable `0x004b3e18`
2. install embedded lock-helper vtable `0x4add70`
3. `InitializeCriticalSection(this+0x08)`
4. switch to live vtable `0x004b3e20`
5. recreate the lock-helper vtable at `+0x04`
6. create event handle and store it at `+0x20`

### `CMessageConnection` relationship

`CMessageConnection_ctor` (`0x448b40`) can allocate two of these helpers:
- connection `+0x7c` = connect/type-2 completion helper
- connection `+0x80` = close/type-1 completion helper

`CMessageConnection_OnOperationCompleted` then does:
- work type `2` -> enter helper lock, `SignalEvent`, leave helper lock on `+0x7c`
- work type `1` -> same pattern on `+0x80`

The startup auth/margin path often leaves both pointers null because the constructor there uses the
flag-disabled path.
