# VTable `0x004c0564` - first concrete heap-buffer helper on the `0x004c0540` base

## Current best read

This is the first concrete derived table on top of the abstract refcounted base at `0x004c0540`.

The exact semantic class name is still unresolved, but the concrete storage added by this table is
already clear enough to document:

- `+0x04` = non-interlocked refcount
- `+0x0c` = owned heap buffer pointer
- `+0x10` = secondary pointer / payload-base-style pointer

## Destructor / layout evidence

`0x481700` is the concrete dtor body used by deleting dtor `0x483060`.
It:

- reinstalls vtable `0x004c0564`
- frees the heap pointer at `+0x0c`
- collapses the object back to base vtable `0x004c0540`

That is the main proof that this table is the first concrete “owned heap buffer” layer on the
`0x004c0540` base.

A later cross-check against `0x4830f0` also tightens its role:
- this heap-backed leaf is the **fallback** storage class when the concatenated source spans are
  larger than the fixed inline capacities offered by `0x004c05d0 / 0x004c05f4 / 0x004c0618 /
  0x004c063c`
- `0x4830f0` writes the total byte count to `+0x10`, allocates a separate heap buffer of that same
  size, and then copies the two input spans into the returned buffer from vtable `+0x10`

## Scope caution

Do not read `0x004816f0` here as a work-type getter.
Like `0x004c0540`, this table uses the shared `mov eax,[ecx+4]` helper as a getter over the local
refcount field.
