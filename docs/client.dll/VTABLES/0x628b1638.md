# 0x628b1638

## Current identity

Current best read is that `0x628b1638` is a **`CLTRemoteCommCtx`-like vftable**.

Why this is now high-confidence enough to use:
- `0x623baf60` contains explicit log strings:
  - `CLTRemoteCommCtx::ResetIO called for RCC %d`
- `0x623bc640` contains explicit log strings:
  - `CLTRemoteCommCtx::IsIdle (RCC %d, ...)`
- replacement crash-time logging on the active `D3D Error` path now shows client-shell field
  `+0xd0` pointing at an object whose vftable is exactly `0x628b1638`

That does **not** yet prove the full owning higher-level client class that stores the object at
client-shell `+0xd0`, but it is enough to treat this vftable family itself as RCC-shaped.

## Active crash relevance

On the replacement-only `D3D Error` route:

Important original comparison from a healthy original-launcher live pass:

  `0x628b1638` object into client-shell `+0xd0`
- later at `client.dll:0x62173bcd`, the original healthy route still had:
  - `client shell +0xd0 = 0x16f9baa8`
  - `*(void**)0x16f9baa8 = 0x628b1638`
  - `+0x68` call returned cleanly with `EAX = 0`
- original sampled object fields on that healthy route:
  - `+0x0c = 0x00000000`
  - byte `+0x154 = 0x00` (low bits clear)
  - bytes `+0x2d8/+0x2d9/+0x2da/+0x2db = [00 00 07 1c]`
  - `+0x2e4 = 0x00000000`

Practical consequence:
- the mere presence of an RCC object at client-shell `+0xd0` is **not** itself the bug
- the remaining question is whether the replacement reaches that same family with subtly wrong
  object state, wrong timing/order, or a bad adjacent runtime tree that later poisons rendering

This is important because the nearby alternate null-vcall family in `ClientShell_RunFrame` uses the
same field:
```asm

62173bd7  mov edx,[ecx]
```

For this vftable, slot `+0x68` is now identified as:
- `0x623bdd60 = CLTRemoteCommCtx_HasPendingState68`

So the null-vcall family is no longer just "some random object method"; it is trying to call an
RCC-state predicate on the object currently stored at client-shell `+0xd0`.
